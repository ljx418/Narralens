## 1. PF01：渲染 origin 必须与被签发的根同源

### 1.1 可达调用链（现状）
1. 用例用**自己的** loopback 服务 `localFolderServer(f.workspaceRoot)`，把 `base: server.base` 传给生产（`native-cache-witness.test.ts:136`、`:302`）。
2. `produceNativeCacheEntry` 把 `request.base` **原样**交给固定 producer（`created-native-workspace.ts:515`）。
3. 固定上游按 `base` 打开**页面**（`pageframes.mjs:90` `pageUrl(base, rel)`），但**按传入的 root** 落盘三件套/海报、并按 root 读依赖身份（`pageframes.mjs:101`、`:178`）。
4. 本实现随后用 **PRE/POST 两棵被签发 root 的闭包**比对依赖与输出身份（`:530`–`:536`、`:568`–`:571`），并激活见证（`:573`–`:580`）。
⇒ 若 `base` 指向**另一自有根**（其中有同名但内容不同的 `film.html`）：绘制的是**别处**的字节，而依赖/输出身份取自**被签发 root**；PRE/POST 身份可全等、输出摘要也与那次**错误 origin** 的绘制一致 ⇒ 见证被激活，而它声称的依赖**并未**提供被渲染的字节。
（预审为静态推论，**未执行**；我的计划同样以静态可达性论证，**不**声称已复现。）

### 1.2 拟代码实体与私有接口（最小）
在 `src/adapters/openfilm/openfilm-upstream.ts`：

```ts
/** 一个**受控**的页面服务 owner：它自己创建并持有真实的 loopback listener、
 *  固定 handler 与 root 身份。 */
export interface OpenFilmServingOwner{
  /** 关闭：停止新的受理；已受理的绘制与真实 raw probe 正常结算。 */
  close():Promise<void>;
  /** 该 owner 的代次（每次创建/重开都不同）。 */
  readonly generation:number;
}
export async function createPinnedOpenFilmServingOwner(vendorRoot:string,root:string,verified?:OpenFilmAvailability):Promise<OpenFilmServingOwner>
```
- 模块私有 `WeakMap<object,{origin:string;root:string;dev:bigint;ino:bigint;generation:number}>` 记录 **origin / canonical root / root 的精确 dev+ino / listener 代次**；**只有工厂能写入** ⇒ 不可伪造 ✔。
- owner **自己** `createServer` 并 `listen(127.0.0.1, 0)`，handler 用**既有**固定 `folderFiles`（默认注入）✔。
- 解析 origin 的出口必须是**模块私有**的：
```ts
export function openFilmServingBinding(owner:OpenFilmServingOwner):{origin:string;root:string;dev:bigint;ino:bigint;generation:number}|null
```
  ⇒ 调用方拿不到「可自报 origin」的入口：拿到的也只是**这个 owner 自己的**记录 ✔。
- 既有 `createPinnedOpenFilmFolderServer`（handler-only）**保留但明确降级为非授权工具**：它不写上面那张私有表 ⇒ 挂到任意 server 后**无法**取得可签字能力 ✔（与设计文件第 12 行一致）。

在 `src/host/agent-driven/created-native-workspace.ts`：
- 服务在**签发 view 时**（或按 view 创建时）为该 root 创建并**私有持有** owner（`#servings: WeakMap<view, owner>` 或按 root+generation 记录）✔。
- 生产入口的 request 改为携带 **owner**（不是 `base` 字符串）✔；服务从 `openFilmServingBinding(owner)` 取 origin，并把 **root 路径 + dev/ino + 代次**与**当前 lease 的 view 目录身份**（服务自己持有的目录句柄 `fstat` ✔）逐项比对 ✔；不符 ⇒ 在 **producer 运行前**拒绝（`NATIVE_CACHE_ORIGIN_FOREIGN` 之类的新码）✔。

## 7. local-assets 并发失败的**只读假设**与确定性复现提案（不作根因结论）

> 状态：**STATIC HYPOTHESIS ONLY**。MAIN 已把只读观察存入控制根 `BATCH_036_LOCAL_ASSET_CONCURRENCY_READONLY_OBSERVATION.json`；
> 下面是**可复现提案**，不是已确立的根因，也**不放宽**任何身份检查。

### 7.1 观察到的形状（不归因）
`tests/agent-driven/integration/local-assets-host.test.ts:310`「bounds real concurrent imports to two and removes a cancelled queued
request without leaking a slot」在 036 中为 22 pass / **1 fail**，失败信息为「Local asset facts or bytes changed」。

### 7.2 我读到的代码事实（`src/host/agent-driven/local-asset-registry.ts`）
1. 同一份内容的**两次并发导入**：各自 staging ✔；随后各自 `link(staging, destination)` ✔（第二次得到 EEXIST 并被容忍 ✔）。
2. 各自对**已发布的 destination** 取一次 blob 证明：`blobProof = await this.#hashFile(destination, input.expected_sha256, true, destinationCanonical)` ✔（约在 :452）。
3. 稍后，在事务内：`this.#assertBlob(destination, blobProof, input.expected_sha256, destinationCanonical)`（约 :476）把**当前事实**与**当时的证明**逐项比较 ✔。
4. `staging` 与 `destination` 是**同一 inode 的两个硬链接** ✔（`link()`）✔；**去掉一个链接会改变该 inode 的 ctime** ✔。
⇒ 假设（未证）：在第 2 步与第 3 步之间，另一次**同内容**发布者结束并**卸载自己的 staging 硬链接** ✔ ⇒ destination 的 inode ctime 改变 ⇒
   第 3 步的 ctime 比较失败 ⇒ 即使**字节完全相同**也被拒为「Local asset facts or bytes changed」✔。
   MAIN 指出 `#assertBlob` **已经显式处理**这一「同字节 ctime」情形 ✔ ⇒ 残留缺口在**证明的取得方式**（`#hashFile` 取到的证明带着当时的 ctime ✔），
   而不是断言端 ✔。

### 7.3 确定性复现提案（不削弱身份检查）
用**既有** `boundary` seam（`this.#boundary?.('before_publish')` 等 ✔）在**第二个**导入的 `before_publish` 时刻制造一次
**同 inode 链接计数变化**（例如对该 destination 再建/撤销一个临时硬链接 ✔）⇒ 目的 inode 的 ctime 改变而**字节不变** ✔；
随后第一个导入的 `#assertBlob` 必然进入 ctime 分支 ✔。
断言：① 第一个导入以「Local asset facts or bytes changed」被拒 ✔（说明该分支**真实可达** ✔）；
② 字节与 content digest **完全相同** ✔（证明这是 ctime-only 的差异 ✔）；③ 两次导入的**内容事实**一致 ✔。
⇒ 由此把「并发同内容发布 ⇒ 误拒」从假设变成**可复现事实** ✔（若复现不成立 ⇒ 假设被否证 ✔，同样是有价值的结论 ✔）。

### 7.4 待 MAIN 决定的两种解法（我不自行选择）
- **A（保守）**：保留严格身份检查 ✔；并发同内容发布允许出现一次可解释的拒绝，由调用方重试 ✔。
  代价：现有「两次并发导入都必须成功」的用例期望需要**按合同澄清**（不是把实现改成迎合错误期望 ✔）。
- **B（对齐已有处理）**：让 blob 证明的取得与 `#assertBlob` 的比较采用**同一套**「同字节 ctime 变化属良性」处理 ✔
  （即证明端不再把 ctime-only 差异记为事实变化 ✔），而 **dev/ino/size/mtime/内容摘要**仍逐项比较 ✔ —— **不放宽身份检查本身** ✔。
⇒ 无论 A 还是 B，都需先有 7.3 的确定性复现与**完整堆栈** ✔；在此之前**不改任何身份检查** ✔。
