## 3. 事务状态机（唯一权威，禁止任意 UPDATE state）

权威状态机（`project_transaction`）：

```
received → preconditions_checked → staged → validated → prepared → committed
   ↘            ↘        ↘           ↘         ↘
aborted / recovering / attention（终态）
```

- **唯一权威写入口** `transition(txId, from, to, patch?)`：
  `UPDATE project_transaction SET state=?, … WHERE transaction_id=? AND state=?`，
  断言 `changes === 1`，否则抛 `INVALID_TRANSITION`。**代码中不存在**不带前态的 state 写入。
- **并发**：同一 `transaction_id` 的两次转换，`BEGIN IMMEDIATE` 串行化；后到者因前态已变而
  `changes === 0` → 抛错，不会写脏。
- **`transition()` 的合法前后态对**（回应 MINOR-6，逐条枚举，实现不得自创）：
  `received→preconditions_checked`、`preconditions_checked→staged`、`staged→validated`、
  `validated→prepared`、`prepared→committed`；
  以及 `{received,preconditions_checked,staged,validated,prepared} → {aborted,attention}`、
  `{received,preconditions_checked,staged} → recovering`。
  **`committed` 无后继**；`recovering` 不由在线代码写入（见 §3.1 映射表最后一行）。

### 3.1 协调器状态机与既有 journal 的关系（回应 MAJOR-1 / MAJOR-2）

`edit_journal` 与 `asset_import_journal` **不能**删除或改名：`tests/host/d3-write-actor.test.ts`
直接断言 `edit_journal.state`，并用原始 `UPDATE edit_journal SET state='prepared'` 模拟崩溃
（AC-019 禁止删除或弱化既有测试）。因此两者**继续存在**，但关系被钉死：

| 维度 | `project_transaction` | `edit_journal` / `asset_import_journal` |
|---|---|---|
| 身份 | `transaction_id`（与 `edit_journal.transaction_id` **同一个** id） | 同一个 `transaction_id` |
| 权威范围 | 跨切面的**协调器阶段**（含 lock / history / import） | 各自 kind 的**恢复明细** |
| 状态词表 | `received → preconditions_checked → staged → validated → prepared → committed`，终态 `aborted`/`recovering`/`attention` | edit：`prepared/source_validated/metadata_committed/aborted/compensated/attention`；import：7 态 |
| 谁读它做决策 | 协调器与写入门（`recoverStatus`、路由 423） | `recoverIncomplete()` 的每 kind 恢复分支 |
| 写入方式 | `transition()` | `advanceJournal(table, id, from, to)` |

**不是两个平行机器**：它们共享同一个 `transaction_id`，且**在同一个数据库事务里双写**。
协调器每推进一个阶段，就在同一事务内同时推进 journal 的对应状态。

**映射表**（协调器阶段 → edit journal 状态；括号内为 import journal 状态）：

| 协调器阶段 | edit journal | asset_import journal | 触发点 |
|---|---|---|---|
| `received` | （无）| （无）| 协调器 `begin()`：插入 `project_transaction`，尚无 journal 行 |
| `preconditions_checked` | `prepared` | `prepared` | 幂等/attention/revision 前置检查通过，journal 行插入 |
| `staged` | `prepared`（不变）| `bytes_installed` | 写入隔离 stage |
| `validated` | `source_validated` | `prepared`（不变）| 后置校验通过 |
| `prepared` | `prepared`（不变）| `manifest_published` | 内容已落定、durability 已证明 |
| `committed` | `metadata_committed` | `committed` | 与 revision / active_commit / idempotency / outbox 同事务 |
| `aborted` | `aborted` | `aborted` | 可安全放弃 |
| `recovering` | （不落该态）| （不落该态）| 崩溃后由 `recoverIncomplete` 判定，非在线转换 |
| `attention` | `attention` | `attention` | 状态不确定或 durability 不可证明 |

「不变」表示该阶段不额外推进 journal 状态（避免无意义的重复写）。

**kind 枚举（回应 MINOR-6）**：`edit`、`asset_import`、`lock`、`history`、`snapshot_publish`。
M2.2 只实现 `edit`、`asset_import`、`lock`、`snapshot_publish`；
`history` 是 M4B 的枚举值占位，M2.2 不写入。

**journal 行的 INSERT（回应 MAJOR-1）**：`advanceJournal` 只做 UPDATE（转换）。
首行 INSERT 由独立 helper `openJournal(table, row)` 完成，它**只被 `preconditions_checked`
这一个阶段调用**，并且与该阶段的 `project_transaction` INSERT/转换处在**同一个**
`BEGIN IMMEDIATE` 数据库事务内（协调器 `preconditionsChecked()` 负责开启该事务）。
因此不存在「journal 已插入但 coordinator 未推进」或反之的中间态。

**`advanceJournal` 改造清单**（现有任意 UPDATE 全部替换）：
`RevisionStore.#state`、`markSourceValidated`、`markAttention`、
`markAssetImportBytesInstalled`、`markAssetImportManifestPublished`、`commitAssetImport`、
`markAssetImportAborted`、`markAssetImportCompensated`。每个都改为带 `from` 前态条件的
`UPDATE … WHERE id=? AND state=?` 并断言 `changes === 1`。

**一致性 fitness**：`tests/architecture/m2.2-fitness.test.ts` 断言
(a) `src/**` 中 `UPDATE … SET state` 只出现在 `transition` 与 `advanceJournal` 内；
(b) 每一个进入 `staged` 及以后的 `project_transaction` 行，都有同 `transaction_id` 的
journal 行或属于 lock/history kind；
(c) 每个 `project_transaction` 的终态与其 journal 终态一致（由集成测试断言，不只靠源码扫描）。

## 4. SnapshotStore / CommitRecord

### 4.1 snapshot 身份（回应 M-E / MINOR-1 / MINOR-4）

```
snapshot_id = SHA256("narralens-snapshot-v1\n" + canonicalJson({ project_id, source_digest }))
```

只哈希 `project_id` 与 `source_digest`（回应 MINOR-2）：`source_digest` 本身已经是
`SHA256("narralens-source-v1\n" + canonicalJson(manifest{files, assets}))`，
**已经把闭包内全部文本与二进制资产的路径/角色/内容摘要钉死**；再把 `files` 塞进 snapshot
哈希既不增加覆盖度，又会让读者误以为它是承重项。内容寻址：相同内容 → 相同 id，
「重复写入即错误」退化为 `snapshot` 主键冲突。提供 `narralens-snapshot-v1` 黄金向量
（TS/Python 跨语言一致）。

`canonicalJson` **唯一取用** `src/host/engine/source-digest-v1.ts` 的导出（回应 MINOR-3）；
`project-write-actor.ts` / `asset-import-service.ts` 内的同名私有实现不得用于摘要。

写入者：`SnapshotStore.persist()`，取值来自**唯一**的 source 定义（回应 MINOR-1）：

```ts
const digest = await computeSourceDigest({
  root: catalog.descriptorRoot(projectId),
  roots: hypitDigestRoots(descriptor),
  engine, engineUpstreamSha,
  declaredAssets,
});
```

即与 M2.1 读取路径同一个函数，不存在第二套 source 定义。

### 4.2 内容格式与原子发布（回应 M-A）

- 内容：闭包内每个文本文件与每个资产按其相对路径原样存放于
  `<var>/snapshots/<project_id>/<snapshot_id>/source/<相对路径>`（raw bytes，非归档）。
- 发布顺序（任一步失败即回滚并进入 attention）：

  1. 写入 `<var>/snapshots/<project_id>/.staging-<uuid>/source/…`
  2. 逐文件 `fsync`
  3. `fsync` 每个子目录，自底向上
  4. `fsync` `.staging-<uuid>/source`
  5. `rename(.staging-<uuid>, <snapshot_id>)`（同目录内原子）
  6. `fsync <var>/snapshots/<project_id>/`（使目录项持久）
  7. **之后**才开启数据库事务：插入 `snapshot` + 更新 `project_state.revision` +
     `active_commit` + `edit_idempotency` + `outbox`
  8. 数据库事务失败 → 删除已 rename 的目录并抛错（仅在同一项目串行边界内发生，见 §11.1）

- **durability**：**不设 durability 列**（回应 MAJOR-3）。snapshot 是内容寻址的，
  「行存在」本身就意味着全部 `fsync` 已成功——没有 `unproven` 取值，也就没有可被写错的中间态。
  任一步抛错 → **不写 snapshot 行、不写 `active_commit`**，而是把
  `project_transaction` 置为 `attention`，`terminal_reason='SNAPSHOT_DURABILITY_UNPROVABLE'`，
  并把 `process.platform` 记入 `attention_reason`。fsync 经注入，故障可注入测试。
  **不存在「已提交但 durability 不可证明」的读路径**：durability 不可证明时根本不发布
  snapshot 行。宁可停工，不猜成功。
- **reader 只读 active committed snapshot**：先解析 `active_commit`（单行）→ 按 `snapshot_id`
  读取；**永不**以目录 mtime 或「最新目录」为来源。
- **导出不漂移**：`render` 收到的 `snapshot_id` 必须由 `active_commit` 解析得到，
  不接受调用方传入；新 revision 不改变在途导出的 `snapshot_id`。

## 5. LockService（三类锁）

锁对象：`scope`(`project`|`shot`)、`target_id`、`start_frame`/`end_frame_exclusive`、
`lock_type`(`visual`|`narration`|`duration`)、`owner`、`reason`、`control_revision`。

**服务端计算影响锁**（`computeAffectedLocks(edit, projection)`，纯函数，可单测）：
- `set_visual_fit` / `replace_visual_asset` → 该 clip 帧区间上的 `visual` 锁；
- 影响帧区间或位置的操作（`timeline.trim/move/split/speed`）→ 该区间上的 `duration` 锁；
- 与 narration/subtitle 共享消费者区间重叠 → `narration` 锁。

客户端 `preserve` 只写入 `project_lock.reason` 作为**意图记录**，永不作为授权；
`preserve` 不影响任何判定。

- 锁增删与 edit 同队列；`control_revision` 随锁变化自增。
- commit 前复核 `control_revision`：漂移 → `409 REVISION_CONFLICT`。
- 锁冲突 → `423 TARGET_LOCKED`。只用既有错误码。

### 5.1 duration/narration 的可达性（回应 M-C）

M2.1 只存在 `set_visual_fit` 与 `replace_visual_asset` 两个 typed edit，且
`replace_visual_asset` 要求资产帧长**恰好等于**选区（`project-write-actor.ts:115-117`），
因此**没有任何 M2.2 可用的 edit 能改变 duration 或 narration**。
处置：

- **LOCK 集成层只断言 visual 锁**（真实 HTTP + 真实 coordinator）。
- `duration` / `narration` 分类器以**合成 edit 载荷**单测（classifier 是纯函数，输入是
  TypedEdit 形状与 projection），并在 manifest 中标 `NOT_APPLICABLE_APPROVED`，
  理由写明「M2.2 无可达的 duration/narration typed edit；集成验证属 M4A」。
- **禁止**把不可达的集成断言写成 PASS。

## 6. PersistentJobStore / Event / Lease

- `NarralensHost.jobs` 在 M2.2 改为 `PersistentJobStore`；既有 `src/host/job-store.ts`
  **保留**为 M2.2 之前的内存实现（AC-019 / ADR D-18），
  `tests/host/host-core.test.ts` 直接构造 `JobStore` 并断言其 `completed_after_cancel`
  行为，**无需修改即可继续通过**；移除 `JobStore` 属后续独立 deprecation ticket（回应 MAJOR-6）。
- 状态：`queued|running|cancel_requested|succeeded|failed|cancelled|attention`。
- **`completed_after_cancel` 读写分离（回应 M-B）**：
  - **写侧**：`transition()` 拒绝任何 `→ completed_after_cancel`；`src/host/server.ts`
    中现有两处发出该状态（late result 分支与 cancel 响应分支）改为
    `cancelled` + `quarantined_*`。旧 literal 不再被写入。
  - **读侧**：`ApiErrorCode`/`JobState` union 与 `contracts/job-response.schema.json`
    **保留** `completed_after_cancel`，既有行仍可校验并原样呈现给旧客户端
    （M2.1 合同测试 `union == schema enum` 继续通过）。
- 必填字段见 §2 `job` 表；新增向后兼容字段 `attempt`、`cost_status`、
  `quarantined_artifact`、`quarantined_receipt`（均为可选，旧客户端可忽略）。
- **CAS lease**（取得）：
  `UPDATE job SET lease_owner=?, lease_expires_at=?, attempt=attempt+1
   WHERE job_id=? AND state='queued' AND (lease_owner IS NULL OR lease_expires_at<=?)`，
  `changes===1` 才算取得。双 worker 只有一个 owner。
- **失 lease 回收（回应 B-2 / MINOR-3）**：**启动时与每 1_000 ms 轮询**都执行 reaper
  （轮询间隔为 Host 配置项 `leaseReapIntervalMs`，默认 1000 ms）：
  `running` 且 `lease_expires_at<=now`：
  - `attempt < max_attempts` → `queued`（经带前态条件的转换，`running→queued` 允许）；
  - 否则 → `attention`（`running→attention` 允许）。
  **绝不** `running→succeeded`。
  由于 CAS 只接受 `state='queued'`，reaper 是把孤儿 job 拉回可获取状态的唯一路径；
  启动与轮询两条路径共用同一个 helper。
- **未知 provider 完成态不自动重试（回应 m-a）**：
  「已知完成态」= worker 显式发出的 `{succeeded, failed, cancelled, attention}`。
  其余（provider 返回成功但缺 `provider_receipt_json`、`cost_status='unknown'`、
  `attempt >= max_attempts`、`cancel_requested` 后再无回调）一律进入终态 `attention`，
  既不回 `queued` 也不自动重试。
- **未知费用不记 0**：`cost_status` 初始为 `'unknown'`，仅在拿到明确金额后转 `'known'`。
- **取消后晚到结果**只能进 `quarantined_*`，不得改 source/revision/采用状态。
- **callback 只登记状态/产物，且必须 CAS（回应 MAJOR-4）**：
  `recordCallback(jobId, patch)` 只允许
  `UPDATE job SET state=?, provider_receipt_json=?, cost_status=?, terminal_reason=?, updated_at=?
   WHERE job_id=? AND state='running'`。
  - `changes === 1`：正常完成。
  - `changes === 0`（原 worker 的 lease 已被 reaper 回收，job 已被另一 worker 接管或已终态）
    → 该回调**判定为晚到**：产物与 receipt 写入 `quarantined_artifact_json` /
    `quarantined_receipt_json`，**不改 `state`**，并记一条 `job.quarantined` 事件。
  - 任何分支都**不触发 commit、不触发 adoption**。
- **reaper 回收时的原 worker 不会被覆盖**：reaper 只在 lease 过期后改 `running→queued`，
  原 worker 随后回来的第一条写入必然 CAS 失败（见上），因此不会出现两个 worker 互相覆盖终态。
- 事件持久、每 job 单调 `seq`、全局单调 `event_id`；SSE `?after=<seq>` 按 `seq` 补发，
  客户端按 `event_id` 幂等去重；`Last-Event-ID` 即 `event_id`。

## 7. Outbox

- 生产者与消费者（回应 M-F）：

  | topic | 生产者 | 消费者 |
  |---|---|---|
  | `project.committed` | 协调器提交事务（同事务写入） | `commit-audit`（写审计视图，幂等） |
  | `job.state_changed` | Job 状态转换（同事务写入） | `job-sse`（投影到 `job_event`，幂等） |
  | `lock.changed` | 锁变更（同事务写入） | `lock-audit` |
  | `recovery.attention` | 启动恢复 | `recovery-audit` |

- commit 与 `outbox` 同一事务写入；发送失败只重放 outbox：`replay()` **绝不重新执行 commit**。
- 语义（回应 MINOR-7）：`outbox.delivered_at` = **全部 consumer 均已确认**的时间；
  每投递一次先查 `outbox_delivery(event_id, consumer)`，已存在则跳过；
  未确认则插入一行并把 `outbox.attempts += 1`；
  当 `COUNT(outbox_delivery) == COUNT(consumer 集合)` 时置 `outbox.delivered_at`。
- consumer 以 `outbox_delivery(event_id, consumer)` 幂等；重复投递不产生第二次副作用。
- commit 状态不确定 → `attention`。

## 8. 启动与门（回应 m-b / m-c）

`recoverOnStart()` 顺序：

```
打开 stores → journal 恢复 → outbox 重放 → 回收过期 lease → 计算 writes_ready
```

- **`markAttention` 新签名（回应 MAJOR-2 / MINOR-5）**：
  `markAttention(projectId, transactionId, errorCode, reason = errorCode)`。
  新参数**可选且默认回落到 `errorCode`**，因此现有 9 个调用点
  （`project-write-actor.ts` 内）**一行都不用改**即可继续编译通过；
  写入时同时写 `project_state.attention=1` 与 `project_state.attention_reason`，
  `reason` 为空串时落哨兵 `UNKNOWN`。
- **reaper 的 attention 写入**：job 因 `attempt >= max_attempts` 进入 `attention` 时，
  调用 `markAttention(job.project_id, 'txn_job_<job_id>', 'JOB_LEASE_LOST_EXHAUSTED',
  '失 lease 且已达 max_attempts 的 job <job_id>')`——
  即 reason 取该 job 自己的 `terminal_reason` 文本，不复用 journal 的。
- `writes_ready` 为**请求期实时计算**，执行点固定为
  `NarralensHost.#createEdit`、`NarralensHost.#importAsset` 与新增协调器写入口的**第一行**，
  在任何 actor / service 调用之前。
- `recoverStatus(projectId)` 的判据**与既有 `RevisionStore.state()` 完全同源**：
  `attention === 1 || #projectHasPending(projectId) > 0`。
  这两条判据抽到**同一个** 私有 helper（`RevisionStore.recoveryGate(projectId, initialRevision)`），
  由 `state()`、`recoverStatus()` 共用，杜绝两处漂移（回应 MAJOR-5）。
- 为 `false` 时短路返回 `423 PROJECT_ATTENTION_REQUIRED`，
  `details.attention_reason` 取 `project_state.attention_reason`
  （由 `markAttention` / reaper 写入最近一次 `terminal_reason`）。
  既有 `ProjectWriteActor` / `AssetImportService` 内部的 423 检查保持不变，
  但由于判据同源，两者结论恒等。

## 9. 验收（逐 case，不以测试总数代替）

| Case | 内容 | 主要断言 |
|---|---|---|
| JB-01 | 重启保留 Job，失 lease 的 running 不假成功 | 重启后 Job 与事件仍在；失 lease → `queued`/`attention`，**绝非** `succeeded` |
| JB-02 | 双 worker CAS 只有一个 owner | 并发 acquire 恰好一个 `changes===1` |
| JB-03 | SSE cursor 补发与去重 | `after=seq` 补发无重复；`Last-Event-ID` 幂等 |
| JB-04 | 取消后的晚到结果 quarantine 且 NOWRITE | 状态 `cancelled` + quarantine 记录；source digest/revision 不变；**旧字面量仍可读** |
| JB-05 | 未知费用不重发、不记 0 | `cost_status='unknown'`；重试不触发 provider 调用 |
| JB-06 | commit 后崩溃只续发 outbox，不重复 commit | 恢复后 revision 不再 +1，outbox 重放幂等 |
| JB-07 | 孤儿 lease 可在**进程内**被回收 | 同进程两并发 acquirer 对 expired-lease running job：恰好一次成功重取，一次 CAS 失败 |
| LOCK | 三类锁 | visual 集成断言（真实 HTTP）；duration/narration 分类器单测 + `NOT_APPLICABLE_APPROVED`；`preserve` 不绕过 |
| SER | 同项目严格串行 / 跨项目并行 | 同项目 N 次写 revision 单调 +1；不同项目互不阻塞 |
| SNAP | active snapshot 不混读 | 并发读只见完整 committed revision；未证明 snapshot 不可读 |
| DUR | commit record durability | 注入 fsync 故障 → attention + 平台限制记录 |
| JRNL | 每个 journal 边界 crash/restart | 六个状态每个边界重启后可判定；无任意 UPDATE state（fitness） |
| BYP | native/HTTP/CLI 绕过均失败 | 未登记 native 入口、直传 `native_operation`、未开放路由分别被拒；**网关位于协调器写路径之前** |
| REG | 旧 D1–M2.1 回归 | `corepack pnpm check` 全绿，既有测试不删不改不弱化 |
| RTE | 路由保持关闭 | materialize/adopt/impact/migrate-copy/history restore 仍 404；虚构 operation 仍 422 且 bytes 不变 |

## 10. 变异门

| 用例 | 注入的违规 | 拥有该门的套件 |
|---|---|---|
| MUT-M | `transition()` 去掉前态条件 | 状态机 + fitness（fitness 断言所有 UPDATE state 都在 helper 内） |
| MUT-N | snapshot 跳过父目录 fsync 直接提交 | durability |
| MUT-O | lease CAS 去掉 `attempt < max_attempts` 回收边界 | JB-01/JB-07 |
| MUT-P | outbox 重放重新执行 commit | JB-06 |
| MUT-Q | 协调器写路径移除网关前置 | BYP，且断言拒绝发生在 `writes.execute` **之前**（用计数探针证明 actor 未被调用），回应 MINOR-8 |
| MUT-R | 锁检查信任客户端 `preserve` | LOCK |

每条必须指向**生产路径上承载该行为的那一行**；若变异后测试仍绿，说明该门未被覆盖，
必须先补覆盖再判定。

## 11. 补充不变量与 fitness

- **11.1 单进程/单队列**：snapshot 的 rename→DB 事务序列只在同一项目串行边界内安全。
  未来若引入多进程，必须重新设计发布顺序。fitness 断言 `NarralensHost` 可达的
  `ProjectOperationQueue` 实例恰好一个。**扫描范围仅 `src/`**（回应 MINOR-4）：
  测试自建 `InMemoryProjectOperationQueue` 实例是合法的。
- **11.2 snapshot 位置唯一**：fitness 断言 `snapshot_id` 字符串在文件系统中只出现在单一
  `var/snapshots/<project_id>/` 根下（回应残余风险 8）。
- **11.3 `preserve` 不授权**：单测断言带 `preserve=["narration"]` 的 `set_visual_fit`
  在存在 narration 锁时**仍被服务端计算结果拒绝**，证明 `preserve` 未被当作授权。

### 11.4 尚无 runner 的 kind（残余风险，非计划缺口）

`proposal_comparison` 是当前唯一有真实 runner 的 kind（`controlled-agent-runner.ts`）。
`render` 与 `snapshot_publish` 在 M2.2 只保证**存储、lease、事件、恢复与 NOWRITE** 语义，
端到端产出属 M6。JB-04/JB-05 与 kind 无关，可对 `proposal_comparison` 做端到端；
对 `render`/`snapshot_publish` 只做 store 层断言，manifest 中如实标注。
