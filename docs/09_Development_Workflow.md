# Narralens 开发治理与协作流程

版本：v1.1（2026-10-12）

本文件记录项目负责人的通用开发流程与开发习惯。它约束后续 Codex 会话中的阶段切换、文档、开发、验收、审计、原型、迁移和汇总行为。

## 1. 单一版本阶段原则与当前硬门槛

- 任一版本阶段（V1、V2……）必须独立完成本文件第 4 节的六步循环；不得把 V1 未完成内容悄悄改名为 V2，也不得在 V1 验收前并行承诺 V2 生产范围。
- 每个版本只有一套获批 PRD、目标原型、目标架构、开发计划和出门门限；新增想法先进入后续版本候选清单，不直接扩大当前版本。
- 当前处于 **V1 第 4 步末端：开发文档迭代已闭环**。V1 原型和开发计划已获项目负责人批准，内部独立审查与两轮 Claude Code CLI 外审均已完成，下一环节是独立“实际开发批准”。
- 在项目负责人明确批准进入实际开发前，不得修改或新增生产功能代码。
- 本阶段允许修改：PRD、架构、计划、验收、原型、审查包、图表、截图证据和相关文档。
- 原型展示不得被描述为已实现的产品能力；规划能力、受限能力和已验收能力必须分开标记。
- 任何阶段都不得以静态页面、模拟数据或截图替代真实功能验收。

## 2. 中断、窗口与设备恢复

### 2.1 中断任务后继续

继续之前中断的自动化开发任务。若不存在可继续的任务，或文档不足以支撑后续自动化开发，或发现虚假验证及其他高风险阻塞点，应停止推进，并向项目负责人提供最近一段相关聊天上下文和明确阻塞原因。

### 2.2 更换电脑后继续

重新建立项目心智模型，明确当前代码、架构设计和开发计划；列出下一步开发计划大纲，并评估现有开发文档对计划的覆盖程度。

### 2.3 重启窗口后继续

报告当前进度；对照 PRD 列出未实现内容。若仍有未完成计划，评估文档对剩余计划的支撑程度；若计划已完成，则列出后续计划或备选目标。

## 3. 原型开发循环

### 3.1 前端原型开发包

- 为 Gemini 准备一份完整、可独立审查、文件数不超过 10 的文件夹。
- 至少包含当前 PRD、源码事实摘要、融合源码或可直接运行的 HTML，以及面向 Gemini 的原型改进提示词。
- Gemini 必须能理解产品目标、目标体验、当前源码基线和不可越过的事实边界。
- 部分组件可直接以代码形式放入原型，但不得进入生产实现。

### 3.2 阶段性原型审查

- 提供一份完整的审查 HTML。
- 保留已认可概念图和当前原型图。
- 新的 Gemini 原型代码只能替换旧原型代码，不得篡改 PRD、架构或能力状态。

### 3.3 阶段性前端优化

审查 HTML 应覆盖：

1. 目标架构概念图与模块图。
2. 当前实际基线页面截图。
3. 结合阶段目标与基线事实的总体设计图。
4. 前端模块详细设计与组件划分。
5. 路由关系与每条用户操作/体验路线。
6. 可交互、可实际操作、有真实样式的组件原型。
7. 每个组件的交互方式、内容和功能说明。

架构和技术流程优先使用 Archify、draw.io、HTML 或 SVG 等确定性表达；图片模型用于概念气氛、内容视觉和适合位图表达的画面。任何 AI 图片进入审查页前，必须检查概念一致性和事实错误。

## 4. 单一开发阶段循环（V1、V2……逐阶段重复）

每一个版本阶段的顺序固定为以下六步，必须闭环后才可开始下一版本：

1. **原型开发**：基于该版本 PRD 和源码事实建立可交互目标原型。
2. **原型审查**：人类审查概念、信息架构、用户路径、能力边界和事实状态；未批准则返回第 1 步。
3. **阶段性原型优化**：把获批方向细化为总体设计、模块、路由、组件、完整状态和用户体验路线；未批准则在第 2–3 步循环。
4. **开发文档迭代**：重复执行“体验对齐 → 开发文档撰写 → 内部文档审查 → 外部文档审查 → 意见修订”，直到 PRD、目标架构、计划、测试、验收和风险足以完整支撑本版本开发与出门验收。
5. **开发迭代**：严格按第 4 步批准的计划逐子阶段执行；每个子阶段独立完成“计划/门限 → 审计 → 实现 → 真实数据测试 → PRD 检视 → 验收 → 证据落盘”，直到第 4 步范围全部验收完成。
6. **阶段性审查**：执行阶段性验收、中文可视化验收报告和 Git 仓同步；代码、文档、Draw.io、真实产物和证据全部一致且人工验收通过后，才关闭该版本并允许启动下一版本。

### 4.0 循环与退回规则

- 第 1–3 步解决“做成什么体验”；第 4 步解决“如何实现和证明”；第 5 步解决“逐项做完”；第 6 步解决“能否诚实宣布该版本完成”。
- 外部审查发现文档缺口，退回第 4 步；开发时发现规格/架构不足，退回第 4 步；子阶段验收失败，退回第 5 步对应子阶段；阶段性审查失败，退回第 5 步，不得跳到下一版本。
- 只有范围变化需要改变用户体验或 PRD 承诺时，才退回第 1–3 步重新审批。
- “批准原型”“批准开发计划”“批准实际开发”“批准版本出门”是四次不同授权，前一次不自动包含后一次。
- 每次状态切换必须更新 `04_Development_Plan.md`、`07_Decisions_Open_Issues.md`、阶段 Draw.io 和交接文档。

### 4.1 交互体验对齐

执行第 3 节的原型交付要求。未获批准前不进入生产代码开发。

### 4.2 开发文档撰写

- 将已认可的开发大纲、原型和 PRD 作为本阶段目标。
- 使用 Archify 重新核对目标架构，并更新 PRD、目标架构、里程碑、验收门槛和 draw.io GAP 文档。
- draw.io 文档使用中文，分页不超过 8 页。
- 图中必须展示具体代码实体、分层、交互关系，以及已实现、开发中、需修改、未开发状态。
- 必须覆盖目标与当前架构差异、开发与验收计划、里程碑、验收门槛和出门条件。
- 验收章节必须包含用户场景、操作步骤、证据和明确出门门槛。

### 4.3 内部风险闭环

- 检查问题是否已经落盘到相关 Markdown 和 draw.io 文件。
- 核对文档是否完整支撑本阶段开发、是否偏离 PRD 或目标架构、是否能支撑出门验收。
- 有缺口时继续文档开发；高风险无法消减时列出风险、备选路线和优劣，交由项目负责人选择。
- 最后打开 draw.io 供人工审核。仍不得进入生产代码开发。

### 4.4 外部文档审查

- 独立复核 PRD、目标架构、开发与验收计划。
- 自行进行多轮文档审计。
- 审计包文件数小于 20；若确有必要，再交 Claude Code CLI 审计，并列出具体文件路径和审计重点。
- 文档不足时继续修订，不得以“待开发时再确认”掩盖阻塞性缺口。

### 4.5 外部意见修订

从 PRD 覆盖、架构合理性、测试覆盖和交互一致性四方面吸收 ChatGPT、Codex 或其他外部意见。修订后重建不超过 20 个文件的平铺审计包，并再次判断是否足以支撑下一阶段自动化开发与验收。

### 4.6 第 4 步的闭环条件

- 原型、PRD、架构、追踪矩阵、开发计划、测试计划、验收门限和 Draw.io 使用同一组概念与状态。
- 内部独立审查和外部文档审查均无未关闭致命/重大问题。
- 每个 P0/NFR 都能追踪到代码实体、子阶段、测试编号和真实证据。
- D1 等未知上游事实必须被显式 Gate 隔离，并规定事实回填位置；不得通过猜测把文档写成“完整”。
- 项目负责人明确批准进入实际开发后，才从第 4 步进入第 5 步。

## 5. 开发执行规则

只有项目负责人明确批准后方可进入。

- 顺序实现所有已被文档完整支撑的计划。
- 每个子阶段开始前，根据总 PRD 形成详细开发计划和验收标准，并单独落盘。
- 实质开发前闭环全部致命和重大审计意见。
- 每个子阶段结束后执行端到端验收和 PRD 规格检视。
- 全程使用真实数据和真实产物；验收不通过时退回计划阶段。
- 若发现较大规格偏差、虚假验收风险或高风险流程，停止并请求项目负责人确认。
- 自动化停止时必须说明停止原因。

### 5.1 单个开发子阶段循环

1. 从 PRD 与追踪矩阵提取本子阶段唯一范围。
2. 写入该子阶段的开发计划、验收步骤、真实数据和证据清单。
3. 闭环致命/重大审计意见。
4. 实现代码，不扩大范围。
5. 执行契约、单元、集成、E2E、真实产物与失败恢复测试。
6. 对照 PRD、目标架构和 Draw.io 检视偏差。
7. 验收通过后更新 evidence manifest、实现状态和下一子阶段准入；失败则在本子阶段内返工或退回第 4 步。

## 6. 阶段性审计与验收

### 6.1 阶段性验收

- 基于原始 PRD 执行代码检视、文档审计、功能检查和全量端到端验收。
- 核对功能实现、测试覆盖、概念一致性和目标架构达成情况。
- draw.io 必须同步到当前实际代码；只有开发内容、目标架构和出门条件全部达成时才能标记全绿。
- 打开本阶段 draw.io 供人工审核。

### 6.2 可视化验收报告

- 输出中文 HTML 验收报告，包含截图证据、目标与当前架构、真实用户体验路径和诚实结论。
- 所有自动化浏览器、交互、截图和端到端测试必须使用 Headless 模式，无声、无可见窗口、无弹窗且不得抢占桌面焦点。不得自行降级为 headed/桌面键鼠自动化；只有用户明确发起的人工验收可以打开可见界面。
- 测试结束后清理相关浏览器实例。
- 打开报告并在对话中给出验收评价和重点。

### 6.3 其他 Agent 复核

若报告不能让人类完整审计本阶段工作，则补充证据或重做报告。出现架构与 draw.io 不一致、承诺未实现、阻塞性测试失败、计划未完成或偏离 PRD 时，必须拒绝声明阶段完成并退回开发。

### 6.4 人工验收

打开最终 HTML 审查文档，重新构建产物并启动服务；在对话中给出最小体验步骤和具体用户场景。

## 7. Git、进展同步、展示与迁移

### 7.1 Git 提交

阶段验收后清理工作树并提交、同步到 Git 仓库。不得删除或覆盖不属于当前任务的用户成果。

### 7.2 项目进展同步

在明确执行项目汇总时，使用本机 `sync-project-progress` skill 同步进展和开发计划到私人助手。

### 7.3 对外可视化展示

在 `docs/present/` 制作项目介绍 HTML 和配套图片，至少展示：

- 当前能力：已验收、受限完成、规划中、No-Go。
- 目标形态及用户使用路径。
- 基于本地文档和外部官方资料的应用前景。

文生图仅服务文档展示，不计入主开发计划，也不能改变能力状态。

### 7.4 项目迁移

换机前把项目、必要文档和恢复上下文提交到 Git；给出最小恢复步骤和可直接交给新 Codex 窗口的恢复提示词。大体积视频素材不进入代码仓库。
