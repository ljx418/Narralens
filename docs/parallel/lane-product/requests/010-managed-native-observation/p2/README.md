# P2 request-start fencing correction

MEDIA independent read-only review found a real P2 in the prior candidate (`71135c54f97672d698e9d24741b67f7e98fca4900757b7484ec9d324a06c867a`): fromServer invalidated when issuing GET, but a late response unconditionally called serverDocument. An old response arriving after a completed newer edit could receive a fresh epoch, turning an invalidated request back into apparent document proof. Earlier tsc/build0 did not exercise or disprove this race. This is a reviewer-found source defect, not a fabricated failed runtime test.

Only exported use-film.ts observation metadata changes in this correction. Immediately after refresh invalidation, fromServer captures requestEpoch. After await, proof requires mounted && current epoch === captured epoch. Dirty, newer refresh, replacement, external edit, unmount or another proof transition all invalidate it. A stale response still performs the same upstream native reducer/value/onChange behavior, but document is null. Before that stale response changes UI it also invalidates a newer proof, so a previously observed B cannot remain displayed as confirmed when stale A overwrites the actual editor. No aborted request, reducer rewrite, added fetch, changed queue ordering, undo algorithm or new store is introduced.

The fence is deliberately conservative. When old A returns while newer C is also in flight, A's actual UI replacement invalidates C's request-start epoch too. C may subsequently update the same original editor but remains unconfirmed; a later uncontended current read can restore proof. Safety does not depend on the old native reducer ordering being fixed.
