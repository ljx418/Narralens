## 4. 分级验证与独立审查

1. 计划先冻结用户场景、真实入口、失败模型、不变量、case映射、证据来源和资源/授权；不能先实现再选有利门槛。
2. 实施者先跑局部类型/合同与关键反例。涉及进程信号、回收或可信授权的改动，在实际运行前做针对性独立安全审查；该前置门不可因提速取消。
3. 安全前置门通过，发布绑定当前源码/固定工具/路径/命令的实际运行票，尽早验证一条最小真实正常链及一个关键失败链，再扩充完整故障矩阵。合成协议、真实内核、真实视频和人验分别标注。
4. 修复后按变更影响复验：修改实体、直接调用者、依赖不变量、对应负例与适用历史回归。复用证据须验证输入摘要一致、场景/环境仍适用且不受变更影响；纯测试不替代内核/媒体证据。不可借“只验差异”漏掉跨层影响。
5. 批次集成和阶段冻结时跑适用全量、构建、安全、真实端到端及四视角审查。独立审查绑定完整冻结commit，修复后新冻结并审受影响内容；出现新共同根因时扩大审查范围。无独立结论标REVIEW_PENDING。
6. 测试工具尽量复用同一受审启动/清理/报告/证据实现；场景差异由输入和断言定义。先审查复用边界，不能让工具和被测实现共享同一个错误判定而相互自证；保留独立内核观察、黄金向量或原始产物校验。

无需每个小修都重复全量审查或请求人工确认。涉及越权发信号、数据损坏、错误授权、无法证明释放等阻塞必须先闭环，不能降级为体验问题留后处理。不能挑绿捕获、放宽超时掩盖错误或把unknown归为环境噪声。
