# Assessment A — 独立设计评估

日期：2026-11-09。目标：`docs/agent-driven-v1/s0-r3/prototype.html`。评估者：`/root/ux_design_assessment`。方法：Impeccable critique Assessment A + UX Researcher，Operate模式。未接触B或detector结果，未运行detector。依据委派任务中的产品约束评估，人物与行为预测均为假设，不是真实用户研究。

## 独立判断

界面表达了“谨慎地运行系统”，还没有充分表达“帮创作者做好当前镜头”。提交、编辑区同步和模型管理有产品相关性，但六格顺序步骤和等权状态卡可以移植到很多作业工具。最大的机会是保留原生编辑器、顶部可折叠横向工作流和独立系统抽屉，把信息组织成当前目标、当前镜头、待判断结果和现在可做的动作。后台阶段作为可展开解释。

历史编辑器截图不能操作不属于生产缺陷；模拟按钮未接后端也不属于本评估的问题。准备中没有可批准结果合理，需要补充的是待确认、回改和局部返工状态的设计。

## 三个优点

1. 不伪造成功：服务启动、装载、预热、就绪分别表达，未知结果保持未知。`prototype.html:8–11,15,18`。
2. 后台信息可收起：工作流默认折叠，系统控制独立打开，保留已有编辑器及导演控件工作模式。`:4–7,16,18`。
3. 保护已有创作：范围、旁白、时长和工程未写入明确可见，共享资源和活动任务限制就近说明。`:4–5,8–10`。

## 五个优先问题

### [P1] 管理系统比判断镜头更显眼

**位置与证据**：`:4`唯一实心主按钮是“系统控制”，当前镜头和“尚未提交”只是文本。`:5,13–17`没有候选预期改变、当前判断点的布局；点“等待确认”也只产生通用“复查当前步骤与公开输入输出”。不要求准备中的状态立刻可批准。

**影响**：创作者首先被邀请管理服务，没有同等级的“在等什么、如何判断、何时介入”。

**方向**：顶部主行表达“镜头2 · 替换画面，保留旁白/时长 → 候选准备中”；完成时主动作变为“查看候选”。待确认展示变化、比较结果、保留约束及继续/改要求入口。系统入口保留独立性，默认弱化，发生阻塞时提升。建议`shape`、`clarify`。

### [P1] 展开条占用高度，没有提供等量决策价值

**位置与证据**：`:2`的`.workflow/.rail/.step`与`:5,14`；`prototype-flow-expanded.png`。独立1440×1000浏览器实测：编辑器图像顶部从94.36px下移到260.31px，损失165.95px可见高度。展开截图时间轴底部超出视口，六个阶段占接近相同面积。

**影响**：理解后台进度需要牺牲时间轴可见性；稀疏流程卡片与密集原编辑器并置，密度不均。

**方向**：保留横向可折叠结构，改紧凑阶段轨道，仅当前节点展开目标/结果/待处理信息。范围和约束并成一行。按常用桌面高度评审“展开后仍能看见预览和时间轴”。不从缩放截图推定必须重构原编辑器。建议`layout`、`distill`。

### [P1] 单向六阶段缺少真实创作的反复和局部返工

**位置与证据**：`:13–14`固定六阶段顺序；`:17`所有节点点击只替换同类说明。没有展示准备中改意图、只重做一个镜头、保留其他结果、已完成检查因要求变化而失效的状态。

**影响**：容易被理解为必须一路完成的向导，用户需要的早期介入没有明确位置。

**方向**：保留后台轨道，增加以目标和镜头为锚的当前工作；设计“要求已变更，候选需重算”“仅镜头2返工”“已提交版本/当前候选”。提供当前范围的改要求、暂停及恢复，说明保留什么。不要新增聊天应用或第二条时间轴。建议`shape`。

### [P2] 系统按基础设施分类，却未关联创作阻塞

**位置与证据**：`:7–10,18`服务/模型/恢复三标签；“生图运行配置”“依赖检查失败”没有具体镜头关联。实测580px模态抽屉覆盖原导演面板并阻塞原页；见`prototype-system-models.png`。操作反馈只更新底部全局消息。

**影响**：需要记住编辑器目标，再判断哪个基础设施项有关；反馈和源条目分离。

**方向**：保留独立抽屉，顶部加“镜头2候选准备受影响：媒体服务未启动”及恢复入口；技术细节放对应标签。反馈就近展示。评审是否仅高影响确认需阻塞编辑，不能将模态一律判错。建议`clarify`、`layout`。

### [P2] 新增交互的键盘和状态语义不完整

**位置与证据**：`:7,17`三个`role=tab`均为`tabIndex=0`，无方向键/Home/End逻辑；工作流`.current`无`aria-current=step`；详情更新没有播报。按钮焦点轮廓和全局`aria-live`是已有优点。

**影响**：键盘和屏幕阅读器用户需额外探索当前步骤及标签操作惯例。

**方向**：设计验收要求单一标签入口、方向键、选中和焦点语义；当前阶段程序化表达，详情更新适当关联与播报。只评价新增组件，不评价截图编辑器。建议`harden`、`audit`。

## 认知负荷

| 清单 | 结果 | 依据 |
|---|---|---|
| 单一焦点 | 失败 | 系统主按钮、流程、导演控件竞争。 |
| 分块≤4 | 失败 | 六个可点阶段同组。 |
| 关联分组 | 通过 | 范围/保留项相邻，抽屉条目分组。 |
| 视觉层级 | 失败 | 六格等权，系统入口强于创作判断。 |
| 一次一个决定 | 通过，部分 | 抽屉一次一个标签；仍缺主任务关联。 |
| 选择≤4 | 失败 | “选哪个阶段复查”同时可选六项。不是要求删除六阶段。 |
| 工作记忆支持 | 失败 | 模型/恢复和镜头目标分离。 |
| 渐进披露 | 通过 | 工作流可折叠，系统按需打开。 |

**5/8失败：按技能清单属于高额外认知负荷**，不是实测工作记忆。视频创作内在负荷高；额外负荷来自将镜头意图翻译为阶段、版本和服务状态。服务标签有多个独立资源，不把不同条目的操作伪算为同一个超四选一决定。应保留有价值的学习：请求不等于就绪、提交不等于编辑器已加载；通过结果和即时反馈讲清，避免要求用户先学runtime术语。

## 情绪旅程（假设）

熟悉原编辑器带来掌控感；“尚未提交、旁白时长保持”带来安心。展开后时间轴下沉、六阶段待解读，注意力变成监工。诚实的“进度未知”仍缺“现在可做什么/何时需要我”，可能形成焦躁谷底。恢复状态可信但技术语言和模态隔离增加切换成本。候选判断和回改状态未设计到位，缺少“这次修改符合预期”的积极峰值。结束应把成功表达为具体镜头已更新、可回看和可撤销，而不止流程完成；现有提交/同步区分是好基础。
