# D4.2 素材实体化与方案采用开发及验收计划

版本：v0.4（2026-10-14，D4.2.1 运行时边界细化）

状态：D4.2 总体方向、修订后的子阶段边界均已通过内部独立审查与 Claude Code CLI 两轮针对性复审。D4.2.1 生产实现、全量 126/126、Headless 浏览器 100%/原生 200% 及内部总审计已完成，独立外部总审计尚待恢复；外审关闭前不得宣告 D4.2.1 通过。D4.2.2/D4.2.3 仍受前序子阶段门禁约束。

## 1. 阶段目标

D4.2 关闭“只读比较之后无法采用”的缺口：用户从 D4.1 的 3–6 个方案中选择一个，为每个视觉分段导入或绑定本地、可商用且已登记的 MP4，查看实际影响与许可，再经一次明确确认把该方案作为一个可恢复事务写入 Hypit Author Source。成功后只产生一个新 Narralens revision，真实预览反映多分段画面，原旁白字节与选区总帧数不变。

本阶段直接推进 `P0-07`、`P0-08`、`P0-09`，并复用 `P0-05/P0-06/P0-10/P0-11` 已有基础；不宣称这些 P0 已整体完成。D4.2 是 D4 的最后子阶段，但不是 Gate V1。

## 2. PRD 边界与非目标

### 2.1 必须实现

1. 从浏览器选择本地 MP4，以流式上传方式导入工程内容寻址媒体目录；浏览器和 API 不提交本机绝对路径。
2. 导入时记录用户声明的来源种类、来源标签、可选来源 URI、许可状态和商业使用结论；文件字节、MIME、视频帧数和 SHA-256 由 Host/ffprobe 生成。
3. 允许未清除素材进入资产库，但只有 `license.status=cleared && commercial_use=true` 的 MP4 能绑定并采用。
4. 将一个 D4.1 Proposal 的每个 segment 精确绑定一个已登记 MP4；输入素材不得短于该 segment，较长素材按冻结规则从首帧起确定性裁切。
5. 在写入前显示目标镜头、旧/新结构、每段素材与许可、旁白/时长保持项、revision、真实本地费用状态和阻断项。
6. 通过 `ProjectWriteActor` 串行执行一个类型化 `adopt_materialized_proposal` operation；OpenMontage、UI 和 MaterializeService 不得直接写 Source。
7. `MaterializeRenderer` 在工程 staging 内把各 segment 素材按提案顺序确定性转码/拼接为一个无音频 composite MP4；输出严格等于选区帧数并登记为内容寻址资产。采用复用 D4.0 已验证的 Hypit `media.replace` 类型化 mutation，保留原 shot Window、视觉 Clip 与稳定 `authoring_id`。
8. 失败时补偿到采用前 Source；结果不确定时进入 `PROJECT_ATTENTION_REQUIRED`，禁止继续写。
9. 本地合成作为异步 Job 运行，复用 SSE 阶段、取消和晚到隔离；没有真实百分比时只显示阶段，不显示假进度。

### 2.2 明确不做

- 不接入远程素材检索、下载或生成 provider；这些属于 PRD P1“素材检索与生成服务适配”。来源 URI 仅是元数据，Host 不抓取。
- 不自动裁剪、变速、补帧、图片转视频或合成图形；本阶段只接受与 segment 帧数精确相等的 `video/mp4`。
- 不采用跨镜选区；仍只允许 D4.1 绑定的完整 registered shot。
- 不实现旁白/时长的主动编辑，也不改变 NarrationBlock；`preserve` 在采用请求中固定同时包含 `narration` 与 `duration`。
- 不实现历史版本 UI、撤回或恢复；采用事务失败补偿属于 D4.2，用户历史恢复属于 D5。
- 不把素材库、materialization record 或 SQLite 事件变成第二条最终时间轴。
- 不把 Proposal 的 segment 升级为新的顶层 Narralens shot；D4.2 在一个稳定 shot 内合成多段画面。逐 segment 再编辑属于后续明确设计，不以 SQLite sidecar 冒充 Hypit 时间轴。
- 不自动重试导入、实体化、本地合成、Hypit mutation 或真实构建；用户可在错误纠正后显式重试。

## 3. 用户体验冻结

1. D4.1 比较完成后，当前选中方案显示“准备采用”，不是直接“采用”。
2. 进入素材准备区后，每个 segment 显示 role、视觉意图、目标帧数、需求说明、当前绑定、来源和许可。`source.kind=generated` 必须独立显示“合成/生成画面”标记；许可 cleared 只表示可用性，不代表真实现场或事实证据。
3. 用户可从资产库绑定，也可通过文件选择器导入 MP4。导入前必须填写来源种类与标签、许可状态、商业使用声明；未知或受限许可可保存但显示阻断。
4. Host 检验失败时聚焦到对应 segment/素材，保留其他绑定和表单；不得显示伪成功或伪百分比。
5. 全部分段满足门限后生成“采用前确认”：旧结构一段、新结构 N 段、相邻镜头不变、旁白 SHA 保持、总帧数保持、manifest SHA、实际本地导入费用为不适用。没有 provider 报价时不得显示估算金额。
6. 用户勾选“我已核对来源/许可与影响范围”后才能提交。视觉锁、旧 revision、manifest 变化或 materialization 过期必须在服务端再次阻断。
7. 成功后显示新 revision、事务 ID、每段资产和真实预览入口；比较结果仍可读但标记为“已采用到 revision N”。
8. 取消素材准备不写 Source；导入成功但未采用的素材可留在内容寻址资产库，不得伪称已进入时间轴。
9. 360/768/1440/1920 宽度及 200% 文本无横向溢出；上传、绑定、许可确认、影响预览和采用可全键盘完成。

D4.2.1 另冻结两份公开 transport response：`d4.2.1-asset-import-response.schema.json` 与 `d4.2.1-asset-inventory-response.schema.json`。完整 manifest 含 `project_path`，不得直接作为浏览器库存响应；库存响应必须让 restricted/unknown 可见并提供 availability/eligible/blocking facts。

进入对应子阶段时才复制为根 `contracts/` 权威运行时 schema并注册 AJV；D4.2.1 只注册 import metadata、AssetManifest v2 和两份公开响应，materialize/adopt 继续 docs-only。文档快照和运行时 schema 的 SHA/语义关系写入 `docs/contracts/README.md`。AssetRegistry 在读取时兼容现有 `narralens.asset-manifest@1`。对 @1 工程，第一次成功提交的新 identity 导入是唯一迁移触发点：同一次原子 manifest transaction 将全部旧条目和新条目写成 `@2`；校验失败、上传取消、幂等命中、重复 identity 和任何提交前失败均保持 @1 原始 bytes，替换后重读失败则从 transaction preimage 原子补偿。提交成功后 @2 成为唯一活跃清单，不保留第二份运行时清单，也不自动降级；需要回退版本时只能使用验收过的工程备份/恢复流程，不能让 Host 暗中丢弃新登记项。v2 增加 `source.kind=derived` 与输入 SHA lineage，禁止把普通拼接误标为 AI synthetic；`generated` 仍只表示合成/生成来源。D4.2.1 的 import 不创建 derived，但 reader 必须兼容已有合法 @2 derived；真正创建 composite derived 只在 D4.2.2。为无损迁移，@2 保留 @1 已接受的通用 URI；新导入仍由 ImportMetadata 限制为 http(s)，Host 永不访问。清单继续限制为 256 项，与当前 Hypit 安全上限一致；容量耗尽返回 422，本阶段不实现垃圾回收。

### 4.1 本地素材导入

`POST /api/projects/:id/assets/import` 使用 `multipart/form-data`，且只允许一个 `metadata` JSON part 和一个 `file` part，禁止重复 part 与未知 part。Host 以流式方式写入工程内私有临时文件，同时计算 SHA-256；默认文件上限 2 GiB，可由启动配置向下收紧但不能由浏览器放宽。Content-Length 存在时非法或超过文件上限加固定 envelope 预算则早 413；缺失 Content-Length 仅在合法 chunked transfer 时允许，并以实际 request/file 双层流计数强制上限；声明长度永远不能替代实际计数。该 transport envelope 不能由 JSON Schema执行，故以审查 schema 根 `$comment` + Host parser + HTTP 集成测试三层冻结，不能把注解误称为运行时强制。完成后以 ffprobe 验证 MP4/单一视频流/CFR/帧数，并以 ffmpeg 做完整视频 decode scan，再原子安装到 `media/<sha256>/source.mp4` 并原子更新 asset manifest。D4.2 不隐式变速或把原生帧数冒充工程帧数；错误帧率/VFR/损坏媒体返回 422 `INVALID_MEDIA`，媒体工具不可用/Host 级超时返回 503 `MEDIA_TOOL_UNAVAILABLE`。输入宽高和像素格式可不同，MaterializeRenderer 的 composite 输出必须匹配当前目标镜头的宽高、yuv420p 和工程帧率（真实 fixture 为 1280×720、30fps）。

客户端只提供：`idempotency_key/source.kind/source.label/source.uri?/license.status/license.label/license.commercial_use`。`asset_id/project_path/sha256/media_type/kind/duration_frames` 全由 Host 生成；`source.uri` 不会被访问。`asset_id=asset_<sha256(canonical {bytes_sha256,source,license})>`，`project_path` 只由完整 bytes SHA 确定；因此重复字节与相同元数据返回同一 asset，重复字节但不同声明产生不同 asset ID、复用同一只读 bytes 且不得覆盖旧声明。同 key 不同内容或元数据返回 `409 IDEMPOTENCY_KEY_CONFLICT`。导入响应的 `manifest_format` 必须反映提交后真实清单格式：@1 精确重复保持并返回 @1；只有成功追加新 identity 才迁移并返回 @2。许可字段含义冻结为：`status=cleared` 是当前采用就绪状态，因此 schema 强制 `commercial_use=true`；`restricted/unknown` 即使 `commercial_use=true` 仍不可采用，因为可能存在归属、地域、时限或署名等其他限制。`generated + cleared` 是合法组合，表示合成画面已获使用许可；UI 仍必须从 source kind 推导并展示 synthetic，不得把 cleared 解释为真实现场。

资产清单修改与 Source 写入共享每项目串行队列，但不增加影片 revision；其并发事实由 manifest SHA 约束。临时文件只位于工程受控 staging，失败只删除本次私有临时项。

### 4.2 实体化请求

`POST /api/proposals/:proposalId/materialize` 接收：

```json
{
  "comparison_id": "comparison_...",
  "base_revision": 2,
  "idempotency_key": "materialize:...",
  "segment_bindings": [
    { "segment_id": "segment_a", "asset_id": "asset_..." }
  ]
}
```

必须恰好覆盖所选 Proposal 的所有 segment，segment 不重不漏且每段一个 asset。`assets_needed` 是提案阶段的需求说明，不是可执行地址；实际采用权威以 `segment_bindings` 为准。Host 重读 comparison、当前 revision、AssetRegistry 和 manifest；每个输入资产须 bytes/hash/MIME/许可有效，且可解码帧数不得短于对应 segment。D4.2 不隐式循环短素材；较长输入从首帧起按 segment 帧数确定性裁切，影响预览明确显示使用范围。

`POST /api/proposals/:proposalId/materialize` 校验并创建异步 Job，成功结果通过现有 Job/SSE 返回 `materialization_id`。阶段只允许 `queued/validating/rendering/verifying/publishing/succeeded|failed|cancelled|completed_after_cancel`；不发送未经测量的百分比。取消时只终止本次私有 ffmpeg 进程并清理本次 staging；若发布已经完成则如实标记 `completed_after_cancel`。D5 之前 Host 重启可丢失在途 job，但已原子发布的 materialization 可重读，UI 必须如实提示。

MaterializeRenderer 对每段执行固定 filter（从第 0 帧取恰好目标帧数、缩放后 letterbox 到目标画幅、无音频），再按顺序合成为 H.264/yuv420p/工程帧率 MP4。参数、ffmpeg 版本和输入顺序进入 canonical recipe SHA；同一 recipe 幂等复用同一 composite。ffmpeg 使用固定 executable 与 argv 数组，不拼接用户 shell 字符串。输出必须经 ffprobe 证明帧数、尺寸、帧率、无音轨和完整解码，再作为 `source.kind=derived` 的 cleared 派生资产原子加入 v2 manifest；`source.lineage` 列出全部输入 asset SHA，许可摘要只有在全部输入 cleared/commercial 时才可 cleared。Manifest v2 schema 与 Host semantic validator 双重强制 `derived ⇒ lineage 非空、license.status=cleared、commercial_use=true`；非 derived 条目禁止 lineage。

编码 profile 冻结为：目标宽高取当前目标 shot 资产的可解码视频流且必须为正偶数；每路使用 `trim=start_frame=0:end_frame=<segmentFrames>,setpts=PTS-STARTPTS,scale=<W>:<H>:force_original_aspect_ratio=decrease,pad=<W>:<H>:(ow-iw)/2:(oh-ih)/2:color=black,setsar=1,format=yuv420p`，随后 `concat=n=<N>:v=1:a=0`。输出 argv 固定包含 `-an -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p -r <projectRate> -frames:v <totalFrames> -threads 1 -map_metadata -1 -movflags +faststart`。recipe canonical JSON 包含 ffmpeg/ffprobe 版本、输入 asset ID/SHA、每段帧数与顺序、W/H/projectRate、上述 codec/profile 参数；输出不得携带 wall-clock creation metadata。实现前用同一机器同一 recipe 连续运行两次，要求 composite SHA 相同，否则停止并冻结更严格参数或改用“recipe 幂等、bytes 非确定”的诚实模型后重新外审，禁止假称确定性。

实体化成功原子写入 `proposals/materialized/<materialization_id>.json`。记录包含：project/comparison/proposal/base revision、selection、proposal canonical SHA、发布时 manifest SHA、composite asset ID/SHA、canonical recipe SHA、每段 role/duration/输出 `[start_frame,end_frame_exclusive)`、输入 asset ID/SHA/来源与许可摘要、总帧数、`preserve=[narration,duration]`、`renderable=true`、`external_transfer=false`、`materialization_cost={status:"not_applicable",currency:null,amount:null}`、创建时间。它是受信任的采用计划与可追溯合成配方，不是独立最终时间轴；Hypit Source 仍是影片事实源且此时尚未变化。

### 4.3 采用 operation

沿用 `POST /api/projects/:id/edits`，扩展 `EditOperation`：

```json
{
  "op": "adopt_materialized_proposal",
  "shot_id": "shot-001",
  "materialization_id": "materialization_...",
  "approval": {
    "confirmed": true,
    "impact_sha256": "<64 lowercase hex>"
  }
}
```

外层 `EditRequest` 固定包含匹配的 `base_revision`、唯一 `idempotency_key`、完整 registered-shot selection，以及恰好 `narration`、`duration` 两项 preserve。operation 同时携带 `approval={confirmed:true,impact_sha256:<当前 Host 影响摘要 SHA>}`。Actor 不接受客户端直接提交 segment/asset/source/license 数组，而是按 ID重读并校验 materialization，重新计算 impact SHA 并要求相等；这使 UI 或直接 API 调用都必须对当前影响快照作出可审计确认。

`GET /api/materializations/:id` 重新校验 project/revision/proposal、每个引用的输入资产条目、composite 条目与 bytes，并返回影响摘要。发布后无关资产新增不会使配方失效；任一被引用条目的 SHA/来源/许可/可用性变化才返回 409。影响摘要绑定当前完整 manifest SHA，因而任何 manifest 变化都会要求用户刷新确认，但不必在无关新增时重新渲染 composite。`EditResponse` 增加可选 `materialization_id/proposal_id/segment_count/transaction_id/impact_sha256`；旧 D3/D4.0 响应保持兼容。

## 5. 受信任事实与状态机

### 5.1 Materialization 状态

Job 经 `queued → validating → rendering → verifying → publishing` 后发布 `ready` materialization；采用后由独立 append-only adoption event 表达 `adopted`，不篡改原记录。若 revision、comparison canonical SHA、任一被引用资产条目或 bytes 变化，则读取/采用时派生为 `stale`，不在原文件上回写假状态；无关 manifest 条目新增只使旧 impact approval 过期。失败的 draft 不发布，ready 记录全有或全无。

### 5.2 采用事务状态

复用 journal：`prepared → source_written → source_validated → committed`；失败允许 `aborted/compensated`；不能确定或补偿失败则 `attention_required`。journal 新增 proposal/materialization/manifest SHA、采用前视觉结构和采用后期望结构，足以在 Host 重启时判断“未写、已写未提交、已提交”而不保存独立最终时间轴。

### 5.3 并发复核顺序

1. API 合同校验；
2. comparison/proposal/materialization 归属及 canonical SHA；
3. 当前 revision、registered shot、visual lock、attention 与 approval impact SHA；
4. manifest SHA 与每个资产 bytes/hash/MIME/帧数/许可；
5. journal prepare；
6. composite bytes/hash/ffprobe、当前 manifest SHA、Hypit preimage/revision 和稳定 authored identity；
7. 带 `manifestSha256` 的 `media.replace`，目标为 materialization 的 composite asset；Studio 在 mutation 边界安全重载并复核该 SHA；
8. Source/Run/语义、旁白、时长、相邻区域和资产再次验证；
9. revision metadata commit。

步骤 5 后任何授权事实变化都不得继续提交。能够证明 Source 未变时 abort；已经改变则补偿；无法证明时进入 attention。

## 6. Hypit 边界与本地合成设计

D4.2 不新增 Hypit 拓扑 mutation，但当前 fork 的 manifest loader 是启动快照：`loadStudioAssetManifest` 只接受 `@1`，启动后任意 manifest SHA 变化都会抛 `StudioAssetManifestChanged`，且会因任一未清除条目拒绝整个清单。因此 D4.2 必须先对固定 fork做以下窄扩展并固定新 commit：

- `media.replace` contract 增加必填 `manifestSha256`；
- manifest loader 兼容 `@1` 与 `@2`，v2 接受 `derived + lineage`，仍保持 1 MiB、256 项、相对路径和 exact-key 限制；
- 每次 mutation 在任何 Source patch 前读取、完整解析并校验调用方声明的 manifest SHA，不信任启动缓存；解析允许 restricted/unknown 条目存在，但 `resolve(assetId)` 只返回当下 `cleared && commercial_use=true` 的目标；
- 本次 resolve 后到 Source patch 规划/提交期间若 manifest SHA 再变化，仍以 `MANIFEST_CHANGED` 拒绝，不降级为继续写；
- `planMediaReplacement`、Source preimage 和原子 patch 行为不变，D4.0 全部 fork/Narralens/真实媒体回归必须通过。

Studio 只接收 revision、稳定 visual `itemId`、已登记 composite `assetId` 和 expected manifest SHA，由 `planMediaReplacement` 基于 Source preimage 生成 typed patch。Narralens Adapter 不拼接或正则替换 SVML。

多段结构在 `MaterializeRenderer` 中成为真实 composite 帧序列：segment 边界由 canonical recipe 和 materialized record 追溯，最终影片事实由 Hypit Source 引用的 composite bytes 决定。该记录不能被运行时当成可独立渲染的第二时间轴；删除它不会改变已采用影片，缺少它只会损失审计/再次采用能力。此路线保留原 visual Clip/Window 的 `authoring_id` 和完整选区，因此再次定位、D4.0 替换、补偿和后续重新采用仍使用同一稳定身份。

## 7. 不变量

1. 采用前后 selection 总帧数相同，且等于所有 materialized segment duration 之和。
2. narration asset bytes SHA、audio semantic object 和 Narration Track 逐字段不变。
3. 目标 shot 外的 temporal/visual/audio semantic objects 逐字段不变。
4. 目标 shot 引用的 composite asset ID/SHA 与 materialization 完全一致；在每个 segment 起点/中点/末帧抽样时与对应输入素材及 recipe 一致。
5. Source 只由 Hypit typed mutation 修改；Run 只由真实编译产生；SQLite 不可独立重建影片。
6. 视觉锁同时阻断 UI 与 Actor；绕过 UI 直接调用 API 仍返回 423。
7. revision 只在事务 metadata commit 后增加一次；恢复旧内容也不得倒退 revision。
8. 未采用、失败、422、409、423 或取消均不得改变 Source/revision。
9. 导入/实体化不调用 Runner，不产生 provider 费用，不发生外传。

## 8. 错误与恢复语义

| 场景 | HTTP/code | 用户体验与写入事实 |
|---|---|---|
| 非 multipart、缺/重复/未知 part、metadata schema 错误 | 400 `INVALID_REQUEST` | 保留表单；无 manifest/Source 写入 |
| multipart 流超过 Host 上限 | 413 `INVALID_REQUEST` | 立即停止接收并清理私有 temp；manifest/Source 不变 |
| 导入媒体 MIME/container/CFR/帧数/完整解码不合格 | 422 `INVALID_MEDIA` | 保留表单；temp 清理；manifest/Source/revision 不变 |
| ffprobe/ffmpeg 缺失、启动失败或 Host 级超时 | 503 `MEDIA_TOOL_UNAVAILABLE` | 保留表单；不自动重试；manifest/Source/revision 不变 |
| comparison/proposal/materialization 或 revision 过期 | 409 `REVISION_CONFLICT` | 要求刷新并重新实体化；Source 不变 |
| 同 idempotency key 不同请求/文件 | 409 `IDEMPOTENCY_KEY_CONFLICT` | 不覆盖首次结果 |
| 被引用资产/许可改变，或写入窗口内 manifest 再变化 | 409 `MANIFEST_CHANGED` | 相关条目变化须重新实体化；无关新增只需刷新影响确认；Source 不变 |
| 缺资产、hash/MIME/帧数不符、许可未清除 | 422 `MISSING_ASSET` | 精确标出 segment；Source 不变 |
| ffmpeg 合成/ffprobe/postcondition 失败 | 422 `MISSING_ASSET` 或 500 `TRANSACTION_FAILED` | 不发布 materialization；Source 不变 |
| Hypit manifest 安全重载、typed media replace 或写后验证失败 | 409 `MANIFEST_CHANGED`、422 `UNSUPPORTED_EDIT` 或 500 `TRANSACTION_FAILED` | 未写或已补偿；不得假成功 |
| visual lock | 423 `TARGET_LOCKED` | UI/API 同时阻断 |
| journal/结果不确定 | 423 `PROJECT_ATTENTION_REQUIRED` | 阻断后续写并要求恢复 |
| Host/ffprobe/Hypit 不可达 | 503 `HYPIT_UNAVAILABLE` | 保留绑定；不自动重试 |
| 影响摘要未确认或确认已过期 | 428 `APPROVAL_REQUIRED` | 返回当前 impact SHA；Source 不变 |

`MANIFEST_CHANGED` 与 `APPROVAL_REQUIRED` 已存在于 TypeScript `ApiErrorCode` 和 `api-error` schema；D4.2 必须保留现有枚举并补齐对应 HTTP/Actor 行为测试，不能重复定义或改变旧语义。D4.2 的 428 只表示当前采用影响/许可快照尚未被用户确认或确认已过期，不伪称发生外传；未来实际外传/付费 provider 仍须另有 provider 审批事实。

## 9. 开发子阶段与门禁

### D4.2.1 契约、本地导入与资产登记（不得写 Source）

- 冻结七份 docs-only 目标 schema；D4.2.1 只把 import metadata、AssetManifest v2、import response、inventory response 四份同步为运行时合同，并冻结错误码、TS 类型、multipart 流式限制和 AssetRegistry v2 读写/迁移语义；materialize/adopt 三份在本子阶段仍是后续目标合同，不注册尚未实现的 API。
- 实现浏览器本地 MP4 流式导入、Host ffprobe/哈希/许可校验、内容寻址安装、AssetManifest @1/@2 读取、资产列表及 UI 导入/许可展示。若工程仍为 @1，第一次成功提交的新导入就是唯一迁移触发点：在项目串行队列内读取并保留原始 bytes/SHA，把全部旧条目与新条目构造成 @2 私有 temp，严格重验后 fsync 并原子替换；替换后再次读取/校验失败则用原始 bytes 原子补偿。失败、取消或重复幂等命中均不触发迁移；成功后不自动降级回 @1，也不保留可被运行时误读的第二份活跃 manifest。
- 同一子阶段先完成并固定 Hypit fork 的 @1/@2 严格解析、restricted/unknown 可留在 inventory 但 `resolve` 只允许 cleared+commercial、mutation 边界 expected manifest SHA 安全重载和 TOCTOU 复核；Narralens `media.replace` 同步携带 expected SHA。导入路由只能与该 fork commit 一起交付，禁止出现“Host 已写 @2、运行中 Studio 仍为 @1-only”的版本窗口。
- 本子阶段不提供 `POST /materialize`，不创建 segment binding、composite、`MaterializedProposal` 或“可实体化/可采用”成功状态；不得用空文件、占位 asset、模拟 Job 或 `renderable=true` 记录冒充实体化。
- 自动/真实验收必须证明成功导入、各类拒绝、重放与故障前后 Source、Run、narration、revision 均不变，Runner 调用为 0；真实 MP4 可在 Host 重启后从资产列表重读。另在隔离 D4.0 fixture 中执行 fork 单元/集成、manifest 改变后的 typed `media.replace` 与全部 D4.0 回归，证明 v2 迁移不回退已验收能力；该隔离回归产生的 Source 写入不得混入导入 NOWRITE 证据。
- 子阶段内外实现审查通过后才进入 D4.2.2。

D4.2.1 固定实施顺序为：运行时合同/类型 → Hypit manifest 扩展（主要修改点 `vendor/hypit/packages/studio/src/asset-manifest.ts` 及 mutation contract）→ Narralens Adapter expected SHA → fork/D4.0 回归 → AssetRegistry v2 与导入 Host API → UI → 真实导入 NOWRITE/浏览器证据。导入路由在前四步全绿前不得启用。新运行时 schema 必须由 `src/contracts/validator.ts` 注册并同步更新合同枚举测试；目标 fork commit 在实现提交中固定并写入证据 manifest，不以浮动分支名验收。

### D4.2.2 只读实体化、确定性 composite 与类型化采用底座

- 实现 segment binding UI、`POST /materialize` 异步 Job、受控 ffmpeg MaterializeRenderer、canonical recipe、内容寻址 composite 登记、`MaterializedProposal` 原子发布和失败清理。
- 复用 D4.2.1 已固定的 Hypit `@1/@2 + expected SHA` 安全重载底座；本子阶段不得再次改变其许可或路径边界。
- 使用独立 D4.2 fixture 证明三个真实输入生成精确 300 帧 composite，边界帧匹配，materialized record/lineage 可重读，Job 取消/晚到语义真实；Source、Run、narration 与 revision 仍完全不变，UI 只显示“已准备采用”。
- ffmpeg/ffprobe 版本、Renderer contract、fork 测试、D4.0 adapter/真实媒体回归与许可复核通过后才进入 D4.2.3。

### D4.2.3 事务采用与交互闭环

- 扩展 ProjectWriteActor journal、idempotency、补偿、启动恢复和 adopted marker。

## 12. D4.2 出门条件

只有以下全部满足才可声明 Gate D4.2 通过：

- 用户能从一个真实 D4.1 方案完成本地导入/绑定、许可核对、影响确认和采用；
- 真实 composite 帧序列与方案分段一致，Hypit Source 通过 typed media replace 引用该资产，revision 恰好 +1，真实 build/MP4 通过；
- 旁白、总时长和相邻镜头不变量全部通过；锁、旧 revision、缺许可、竞态和失败补偿有真实证据；
- D1–D4.1 回归全绿，无旧测试删除、改名、跳过或降级；
- evidence manifest 与代码/文档/架构状态一致，内部和外部实现审查均 PASS。

出现以下任一情况必须停止并回到路线评估：确定性 composite 无法精确满足帧数/边界抽样；Hypit 无法在不放宽路径/许可/preimage 边界的前提下安全重载指定 manifest SHA；D4.0 typed media replace 回归失败；只能靠正则/文本位置改 Source；补偿不能恢复精确 preimage；本地素材导入只能接受任意客户端路径；许可事实无法在写前后重验；真实构建无法证明旁白/时长/相邻镜头不变；或验收只能依赖 mock/静态截图。

D4.2 通过后的下一动作只能是 D5 文档开发与门禁审查，不得把 D4.2 的事务补偿冒充用户历史恢复。
