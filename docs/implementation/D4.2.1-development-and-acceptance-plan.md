# D4.2.1 契约、本地导入、资产登记与 Manifest 兼容底座开发及验收计划

版本：v0.3（2026-10-14，外审复审通过）

状态：内部独立审查与 Claude Code CLI 第二轮文档复审均通过。生产实现中的合同/共享队列、Hypit manifest lease/Adapter expected-SHA、AssetRegistry/import journal 三个子阶段均通过自动化与只读实现外审 0/0/0；fork 固定为 `6fdd8c0f02c17b9970aee6deb4550a70e9d57acf`。ImportService、multipart/routes、UI 与最终真实导入端到端证据仍未完成，完成前不得声明 D4.2.1 通过。

## 1. 子阶段目标

D4.2.1 只交付一个可独立验收的真实能力：用户从浏览器选择本地 MP4，填写来源与许可，Host 以受限流式上传验证并登记到工程内容寻址媒体库；成功后所有资产（含 restricted/unknown）可在公开库存中重读，只有实际可用且 `cleared && commercial_use=true` 的条目标记为 eligible。@1 工程在第一次成功导入时原子迁移到唯一活跃的 @2 manifest；Hypit fork 与 Narralens Adapter 同批支持 @1/@2、expected manifest SHA 和 TOCTOU，确保已通过的 D4.0 不发生阶段性回退。

本子阶段推进 PRD `P0-08` 的本地获取、来源、许可和可追溯登记，但不宣称 P0-08 完成。导入成功不等于进入时间轴，不增加影片 revision，也不代表方案已素材化或已采用。

## 2. 明确范围与 NO-GO

### 2.1 必须实现

1. `POST /api/projects/:id/assets/import`：同源、Bearer session、严格 multipart、一个 metadata JSON part、一个 MP4 file part、全程流式和 backpressure。
2. `GET /api/projects/:id/assets`：返回不含 `project_path` 或绝对路径的公开库存，显示来源、许可、synthetic、可用性、eligible 与阻断原因。
3. AssetManifest @1/@2 兼容读取，@1 第一次成功导入原子迁移 @2；失败保持或精确补偿原始 bytes。
4. 内容寻址安装、真实 SHA-256、完整媒体探测/解码、单视频流、CFR 与工程帧率一致、正整数帧数。
5. 持久化导入幂等与 crash recovery；同 key 同请求重放同一结果，同 key 异请求稳定 409。
6. 把 `ProjectWriteActor` 私有 tails 抽为 Host 单例 `ProjectOperationQueue`，导入 manifest commit 与既有 Source transaction 按 project_id 共用同一串行边界。
7. Hypit fork 支持 @1/@2、restricted/unknown inventory、eligible-only resolve、mutation `manifestSha256`、重读租约和写前/写后 TOCTOU；Narralens D4.0 Adapter 同步传 expected SHA。
8. UI 提供真实文件选择、来源/许可表单、上传状态、错误恢复和公开库存；已有 D4.0 可替换列表仍只展示 eligible 条目。

### 2.2 本子阶段禁止

- 不注册或响应 `POST /api/proposals/:proposalId/materialize`；该路径必须仍为 404。
- 不创建 segment binding、ffmpeg composite、MaterializedProposal、impact approval 或 adoption event。
- 不显示“已素材化”“已准备采用”“已采用”或 `renderable=true`。
- 不访问 `source.uri`，不下载、不检索、不生成、不调用 Claude/OpenMontage Runner，不产生 provider 费用或外传。
- 导入路径不调用 `ProjectWriteActor.execute`，不写 Hypit Source/Run，不增加 revision，不修改旁白或镜头语义。
- 不接收浏览器绝对路径、目录、file URI、客户端 SHA、帧数、`asset_id` 或 `project_path`。
- 不手写宽松 multipart parser，不把整个文件缓冲进内存，不用文件名构造工程路径。

## 4. 冻结合同

### 4.1 运行时 schema 范围

D4.2.1 只把以下四份审查快照复制为根 `contracts/` 权威运行时 schema，换成生产 `$id`，注册 `src/contracts/validator.ts` 并增加 TypeScript 类型/正反例：

1. `d4.2-asset-import-metadata.schema.json`；
2. `d4.2-asset-manifest-v2.schema.json`；
3. `d4.2.1-asset-import-response.schema.json`；
4. `d4.2.1-asset-inventory-response.schema.json`。

materialize request、MaterializedProposal 与 adopt operation 在 D4.2.1 仍是 docs-only 目标合同，不注册 API，也不以存在 TypeScript 类型冒充能力。生产 `asset-manifest.schema.json` 改为明确的 @1/@2 `oneOf` 或等价严格 union；不能让同一对象同时命中两版。

运行时 `contractIds` 必须精确新增 `AssetImportMetadata`、`AssetManifest`、`AssetImportResponse`、`AssetInventoryResponse` 四项；每项都由 `addSchema` 注册且可通过 `$id` 独立解析。`D421-CONTRACT-04` 必须直接断言四个 ID、注册数量、根 schema SHA 映射和 validator 可解析性；同时断言 `MaterializeRequest`、`MaterializedProposal`、`AdoptMaterializedProposal` 在本阶段不存在于 runtime `contractIds`。

AssetManifest @2 为向前扩展：新导入的 `source.uri` 只允许 `http/https`，但迁移必须逐字保留 @1 曾允许的其他合法 URI；Host 从不解引用 URI。@2 schema 因兼容迁移接受通用 URI，ImportMetadata schema 继续收窄新输入。Host semantic validator 额外拒绝重复 `asset_id`、重复/矛盾 identity、derived 许可/lineage 错误和超过 256 项。

### 4.2 API

`POST /api/projects/:id/assets/import`

- 请求：`multipart/form-data`；part name 只能为 `metadata` 和 `file`，各恰好一次，未知/重复 part、多个文件、嵌套 multipart、非法 boundary 均 400。
- `metadata` 必须声明 `application/json`，UTF-8 bytes 上限 16 KiB；file part 必须声明 `video/mp4`，原始 filename 仅用于本地 UI 显示且不落入路径/manifest/日志。
- 新 identity 成功返回 201 且 `created=true`；已存在的同 identity 首次请求返回 200 且 `created=false`；同一 key/同一 canonical request 的幂等重放必须返回持久化的完全相同 HTTP status/body。`manifest_format` 返回事务完成时唯一活跃清单的真实 `@1/@2` 格式：@1 工程精确重复不迁移，返回 `@1 + created=false + migrated_from_v1=false`；@1 工程成功追加新 identity 后返回 `@2 + created=true + migrated_from_v1=true`；@2 工程始终返回 @2。`migrated_from_v1` 只描述原始成功事务是否完成迁移，重放不重算。
- Content-Length 存在时必须为合法非负十进制且不超过 `file_limit + 64 KiB`，否则早拒绝 413；缺失 Content-Length 仅在合法 chunked transfer 时允许，并由实际流计数强制同一上限。实际 file bytes 超限立即停止、销毁流并清理 temp。不得因声明长度较小而信任客户端。

`GET /api/projects/:id/assets`

- 返回 `AssetInventoryResponse`，保持 manifest 顺序；不返回 `project_path`、绝对路径、浏览器原 filename 或本地 token。
- `availability` 来自请求时的当前 bytes/hash/媒体检查，`eligible` 只在 available 且 cleared/commercial 时为 true；`blocking_reasons` 与事实一致。D4.2.1 不使用跨请求 availability 缓存：每次 GET 都重新做 realpath containment、stat 和流式 bytes SHA；最多 256 项，hash/历史 @1 ffprobe 并发上限为 2，单项超时或工具失败时只把该项标为 unavailable 并给出稳定阻断原因，不把陈旧可用性当真。即使 size/mtime 不变，bytes 篡改也必须在下一次 GET 被发现。后续采用仍独立重验。`generated` 必须由 UI 显示 synthetic；cleared 不改变该事实。
- D4.0 `ProjectResponse.available_visual_assets` 保持兼容，继续仅映射 eligible 条目；新库存 API 承担完整列表，不破坏旧客户端。

### 4.3 标识与 canonical 规则

- `bytes_sha256` 在流式接收时由 Host 计算。
- `asset_id = "asset_" + sha256(canonical_json({bytes_sha256,source,license}))`；canonical JSON 使用排序键、UTF-8、无空白，缺失 `uri` 与空字符串不得等价。
- `project_path = "media/<bytes_sha256>/source.mp4"`，从不使用 filename。
- 同 bytes + 同元数据得到同 asset；同 bytes + 不同合法来源/许可得到不同 asset ID、共用同一只读 media bytes。
- manifest canonical bytes 为排序键 JSON + 单个 LF；保留原有 assets 顺序，新 identity 只追加一次。manifest SHA 对实际落盘 bytes 计算。

## 5. 流式导入与媒体验证

实现使用固定版本的成熟流式 multipart 库（计划锁定 `busboy`，连同类型与许可证进入 lockfile/审计），不自研 boundary parser。`D421-DEP-01` 必须证明 package.json 与 lockfile 固定同一解析版本、类型可编译、许可证文件/声明进入证据清单，且依赖审计没有未裁决的高危项。Host 设置 files=1、fields=1、parts=2、fieldSize=16 KiB、fileSize=启动配置（默认 2 GiB）；同时在原始 request 与 file stream 两层计数，防止 parser/头部开销绕过。pipeline/write stream 负责 backpressure；监听 request aborted/error、parser limit、file error、ENOSPC 和 response close，清理本次 UUID 私有 staging。

文件落入 `<project>/.narralens/staging/import-<uuid>/source.mp4.part`。目录和文件用 Host 生成名；创建时禁止跟随既有 symlink，最终 `realpath`/相对 containment 双验。验证顺序：

1. part Content-Type 与非空 bytes；
2. `ffprobe` argv 数组读取 format/streams、恰好一个视频流、MP4 container、帧率 rational、帧数和宽高；允许音轨存在但不信任/不写入任何音频事实；
3. `ffmpeg -v error -i <temp> -map 0:v:0 -f null -` 完整解码扫描，禁止 shell 拼接；
4. `avg_frame_rate == r_frame_rate == project frame_rate`，帧数为正安全整数；VFR、错帧率、损坏、无/多视频流均 422；
5. 重新读取/哈希 temp，必须等于流式 SHA，防止验证窗口内变化。

进程超时与最大 stderr 均有启动上限。当前生产 TypeScript/`api-error` schema 尚无以下两项；D4.2.1 必须同步新增稳定 code：内容/MIME/CFR/解码不合格返回 422 `INVALID_MEDIA`；ffprobe/ffmpeg 缺失、启动失败或 Host 级超时返回 503 `MEDIA_TOOL_UNAVAILABLE`。`D421-ERRORCODE-01/02` 分别证明 runtime union、schema、HTTP normalization 和 UI 映射一致。不得借用 `HYPIT_UNAVAILABLE` 或把工具故障伪装成缺素材。D4.2.1 不自动变速、补帧、裁切、转码或去音频。

## 6. ProjectOperationQueue 与导入事务

### 6.1 共享串行边界

新增 `src/host/projects/project-operation-queue.ts`，冻结接口：

```ts
export interface ProjectOperationQueue {
  run<T>(projectId: string, operation: () => Promise<T>): Promise<T>;
}
```

同一 `projectId` 按调用进入顺序 FIFO 串行；operation 的成功值/错误原样传给调用方，但一次 reject 不得毒化 tail，后继操作仍可执行。不同 project 并行；队列不做 retry、priority、持久化或业务 attention 判定，attention 只由 SQLite journal/项目状态持久化。Host 只创建一个实例并同时注入 `ProjectWriteActor` 与 `AssetImportService`。Actor 删除自己的独立 tails，所有 D3/D4.0 事务测试必须证明仍按项目串行；上传/解码在队列外完成，只有 commit/recovery 进入队列，避免大文件阻塞既有编辑。

### 6.2 ImportJournal

在现有 SQLite 中新增 `asset_import_journal`，至少保存：project/key、canonical request SHA、state、asset ID、bytes SHA、before/after manifest SHA、是否新建 bytes、response status/body、error code、timestamps。状态：`prepared → bytes_installed → manifest_published → committed`，失败为 `aborted/compensated/attention`。`(project_id,idempotency_key)` 唯一；journal 不插入 revision event、不更新 project revision。

完整 canonical request SHA 绑定 metadata canonical JSON 与最终 bytes SHA。因文件 SHA 未知，幂等只在上传/验证后最终判定；可用已有 key 的 metadata hash 做安全早拒绝，但不得在未验证 bytes 时返回伪重放。

### 6.3 Commit 顺序

1. 进入项目队列，重读 descriptor、当前 manifest bytes/SHA 和 import idempotency。
2. 同 key 同 hash 且 committed：返回持久化的完全相同 status/body；同 key 异 hash：`409 IDEMPOTENCY_KEY_CONFLICT`。
3. 校验当前 manifest @1/@2、所有 identity/路径/许可语义和 256 容量；准备 journal，保存 preimage SHA 与 canonical after bytes/hash。
4. 若内容路径不存在，从私有 temp 同文件系统原子安装并 fsync 文件/目录；若存在则 realpath containment + bytes SHA 一致，否则 attention。
5. 写 manifest sibling 私有 temp，fsync，原子 replace，fsync 父目录；重读 bytes、SHA、schema、目标 entry 和 media bytes。
6. commit journal/idempotent response；清理私有 staging。成功导入不改变 Source/Run/narration/revision。

若步骤 5 后验证失败，用 journal preimage 写 sibling temp 后原子补偿并重读；仅当本事务新建且当前 manifest 无任何条目引用该 bytes 时删除新内容文件/空目录。预期 manifest/授权 bytes 在事务期间变化返回 `409 MANIFEST_CHANGED`；不能证明精确恢复则 import journal 和 project 进入 attention，所有后续 manifest/Source 写拒绝 `423 PROJECT_ATTENTION_REQUIRED`，读取库存仍可返回明确不可用状态。Host `listen()` 在开放端口前恢复所有未完成 import journal，再执行既有 edit recovery；两者使用同一 queue。

### 6.4 @1 → @2

只有 @1 工程第一次“新 identity 成功提交”触发迁移；幂等命中、重复 identity 无新增、校验/容量/上传失败不迁移。精确重复的首次请求和其幂等重放都必须返回真实 `manifest_format=@1`，不得为满足 transport 响应而改写清单。迁移保留旧 entry 的字段值与顺序、追加新 entry；@1 的通用合法 URI 原样保留。成功后 descriptor 仍指向同一 manifest 路径，@2 是唯一活跃清单，不维护 shadow manifest。工程级备份属于验收/运维，不作为运行时双写。

## 7. Hypit Manifest Lease 与 D4.0 兼容

固定 fork 修改实体：

- `packages/studio/src/asset-manifest.ts`：严格 parse @1/@2；@2 `derived + lineage`；inventory 可含 restricted/unknown；`resolve` 只返回 cleared/commercial 且 bytes/路径有效的目标。D4.2.1 不创建 `derived`，导入 metadata 也不接受 `derived`；reader 仍须读取外部兼容工具或未来阶段已合法写入的 @2 derived entry，避免再次制造格式回退。
- `packages/studio/src/shared.ts` 与 `server.ts`：`media.replace` 必填 `manifestSha256`（64 位小写 hex）；无字段/格式错 400，SHA 不同 409。
- `StudioAssetManifest` 提供基于 expected SHA 的 mutation lease：一次完整重读/parse 建立 immutable entries；target `resolve` 只允许 eligible，`identifyLocator` 可识别库存中的现有 binding 但不得把非 eligible 条目变成 mutation target；每次敏感读取前复核当前 manifest bytes SHA。
- `commitMutation` 在生成 patches 前、`applyTransaction` 前、Source 写后/发布前和成功响应前复核 expected SHA。若写前变化，0 Source 写并返回 409；若 Source 写后发现变化，先精确恢复 Source preimage并重新 publish，再返回 409；恢复不确定按现有 mutation failure 机制拒绝假成功。
- Studio 不再把启动 entries 当作后续 publish 的权威。普通只读 snapshot projection 获取当前只读 manifest view；`media.replace` 的 patch planning、post-write publish 与 postcondition 全部使用同一 expected-SHA lease，确保 @2 导入后无需重启 Studio且 snapshot 反映当前 asset identity。
- `HypitWriteAdapter.mutateMedia` 增加 `manifestSha256`，正常写、no-op、补偿和 recovery 均传当前 journal/AssetRegistry SHA；不放宽 origin、path、1 MiB、256 项、exact-key 或 Source preimage 限制。

副作用所有权必须保持单一：Hypit 不复制、移动、下载、安装或回滚 asset bytes，也不写 AssetManifest；Host `AssetImportService` 独占 media bytes、manifest 和 import journal 的安装/补偿。Hypit 只读取当前授权 bytes，并只通过既有 `applyTransaction` / `replaceSourceFiles` 写入或恢复 Author Source。若 Source 已写后检测到 manifest/bytes 变化，Hypit 恢复自身持有的 Source preimage；它不能也不得尝试恢复由 Host 或外部进程改变的 media bytes/manifest。Source 恢复无法证明时进入现有 attention 机制。四次 SHA 复核是 D4.2.1 新增 fork 行为，不是当前 runtime 已具备的能力。

fork 必须先运行 workspace 单测、`asset-manifest.test.ts`、新增 server mutation tests、真实 Studio D4.0 replace；固定新 fork commit 并推送 `ljx418/hypit`，Narralens gitlink 与 Adapter 在同一实现提交消费。导入 route 在该组合全绿前不得开放。

## 8. UI 体验

在现有 D4.0 素材区增加“本地资产库存”与“导入 MP4”区域，不把 D4.2.1 伪装成方案素材化：

7. 360/768/1440/1920、200% 文本、键盘、屏幕阅读器状态与 axe 无 critical/serious；不会弹出系统窗口或抢焦点。

## 9. 实施顺序与文件级交付

## 12. 出门条件与停止条件

D4.2.1 只有在以下全部满足时通过：

- 文档内外审、实现内外审均 `fatal=0 / major=0 / must-fix=0`；
- 四份运行时合同、Host/Registry/Journal/Queue/UI 和固定 Hypit fork均为生产代码且真实测试通过；
- 用户真实导入 MP4、重启 Host 后看见完整库存，restricted/unknown 如实阻断，generated 如实标记；
- @1→@2 原子迁移、幂等、崩溃/磁盘/竞态恢复有真实证据；
- 导入路径 Source/Run/narration/revision 完全不变；D4.0 在 @2 后仍能 typed replace/build；
- 旧 80 tests 加全部新测试全绿，无删除/跳过/降级；evidence manifest 与代码/文档状态一致。

出现以下任一情况立即停止并退回文档：只能缓冲完整上传；multipart 边界无法严格限制；@1 合法事实必须被静默改写/丢弃才能迁移；导入与 Source 写无法共享串行边界；manifest 写后不能精确补偿；Hypit 只能通过放宽路径/许可/expected SHA 才能兼容 @2；TOCTOU 只能事后忽略；D4.0 回归失败；导入会写 Source/revision 或调用 Runner；真实证据只能靠 mock/截图。

D4.2.1 通过后，下一动作是 D4.2.2 子阶段文档开发与门禁，不得直接把已登记素材描述为已实体化或采用。
