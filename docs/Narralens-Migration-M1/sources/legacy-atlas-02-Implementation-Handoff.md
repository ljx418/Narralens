# Codex 增量交接：叙事地图不是第三套剪辑引擎

## 1. 保持原路线

Narralens 统一前端及编辑控制；OpenMontage 用于研究、分镜提案和素材上游；Hypit 是最终已采用工程与渲染基础。此处复述已有基线，不等于本轮安装或重新验证了两个上游。

本次新增的生产模块应是：StoryAtlasView、DecisionFocus、CandidatePreviewPool、DecisionJournal、ContextGate。它们投影同一个主工程，不让自由节点图成为另一份可独立修改的时间线。

```text
用户表达与资料
  -> CreativeBrief / Evidence / ChapterPlan
  -> OpenMontageAdapter + 受控 runner（提案或素材暂存）
  -> CandidateGroup（所属镜头、类别、范围、来源、费用、可用性）
  -> Proxy / Thumbnail / Waveform preparation
  -> StoryAtlasView + CandidatePreviewPool
  -> 用户选择 / 保存意图 / 审批
  -> EditCoordinator（锁 / 基线修订 / 共享消费者 / 幂等）
  -> HypitSourceAdapter（真实工程与所选产物）
  -> compile -> 真实预览 -> render -> QC
```

地图的位置不决定成片内容。每个节点绑定稳定 ShotId / ChapterId / 半开帧范围；采用先改真实工程，再刷新地图投影。未选分支不触发最终渲染，生成产物晚到只进入暂存，不覆盖新编辑。

## 2. 前端实现选择

原型是单文件原生 HTML/CSS/JavaScript，不引入外部库，以便离线体验。

正式应用优先在现有 Hypit Studio 壳和状态组织方式内实现这一视图。React Flow 可作为画布缩放、平移及节点外壳的候选，而非新增必选依赖。[R2] 若现有时间轴已经具备足够的视口和命中基础，应复用它，避免两套选择状态。

不能把全部视频控制权塞进通用节点布局库。x=(frame-viewStartFrame)*pixelsPerFrame；播放头、源媒体、字幕共享时间基准。章节/候选布局在投影层处理。图中拖动画布只是平移视野，不能误触发重排剪辑。

## 3. 解码与代理策略

目标：前端最多同时激活三个可见候选解码器，媒体源是本地代理或授权可访问的文件；选中大预览与三路比较互斥时释放空闲解码器。声音采用单独的试听焦点。

建议代理尺寸先取 540p 或 720p、与目标时间尺度匹配的 5–10 秒窗口，再基于本机能力调优；不是性能承诺。不并发加载 90 × 3 个 4K 文件。预取下一节点两三个低清候选可以做，但本轮原型没有实现后台预取。

缩略图和波形必须来自真实媒体。尚未生成的候选可以显示文本设计，但不能使用假波形或视频加载动画冒充产物。

费用规则：自动播放已就绪代理不产生新生成；自动请求新素材另走提案、预算和审批。自动推荐不等于自动花钱。

## 4. 本次原型的数据兼容

新导出包装：

```json
{
  "kind": "narralens_story_atlas",
  "schema_version": "1.0",
  "project": "完整保留上一版 narralens_experience_session v2 对象",
  "atlas": {
    "decisions": "按稳定镜头 ID、类别记录采用",
    "visited": [],
    "checkpoints": [],
    "history": [],
    "intents": []
  }
}
```

该例说明结构，不是可直接导入的实例。实际项目可以从 HTML 导出。生产数据必须由正式 Schema 校验，不能拿本次演示的嵌套快照作为最终数据库模型。

全部旧字段保留，包括没有迁入 UI 的交付、后期、来源与原历史。导入测试包含额外未知字段保留验证。旧版不能直接读取新的包装；后续应提供显式兼容导出，并提示扩展损失，本轮不伪称已有反向兼容导出按钮。

仅按文件名/大小/修改日期的本地重新关联不够安全，生产版必须使用内容哈希、媒体探测、明确选择不匹配文件的确认。

## 5. 决策事务补充

- 低风险已就绪媒体替换：单击、立即反馈、可撤回，保留底层修订与锁检查。
- 共享台词/声音：显示所有消费者，任一相关锁阻止，后续对齐标 stale。
- 过场：真实相邻边界对象，检查两侧 handle；原型保存意图不能视为过场已经渲染。
- 采用和恢复都不能改变锁定素材或后期参数。
- 选区、类别、旧值和新值、保留项、baseRevision、幂等键必须进入正式 EditRequest。
- 比较/浏览不产生工程修订；素材导入和意图记录可产生元数据修订，但不能覆写已采用轨道。
- 发布状态和选定状态分离；“90 镜已选”不是完成度 100%。

## 6. 实施顺序与阶段门

A. 在固定 SHA 上跑通真实 30 秒多镜工程的编辑、保存、关闭重开和再导出。此门仍未由本轮离线原型满足。

B. 把已有真实工程投影到可缩放的章节/镜头地图，点击节点能定位真实播放器；平移/缩放不得改变工程。

C. 让单个镜头拥有 3 个真实本地视频候选，自动静音比较、采用后写入主工程，源片段和成片时长一致。

D. 建立低风险一击采用、范围影响确认、检查点、冲突和锁保护；再支持沿已选主线播放，在需要人决策时暂停。

E. 接入 OpenMontage 产生结构化候选，而不只返回文字；核验任务运行器、取消、晚到结果、预算和来源。

F. 将六类组成、共享台词/声音、后期、标题封面和事实检查附着到节点。补齐旧精修需求，包括关键帧和局部剪辑，不以新 UI 为由删掉旧能力。

G. 用真实 10–15 分钟、60–180 镜头资料做性能与创作试用。记录解码占用、内存、首帧等待、候选切换与生成费用；缺素材和失败必须可接管。

这些是依赖顺序，不是“几天必定完成”的重新承诺。原先首周精修片/首月长片的取舍仍需用户与技术探测后确认，不在此擅自冻结。

## 7. 禁止 Codex 顺手扩张

不重写底层 NLE，不做通用工作流平台，不把平面编辑替换为必须旋转的三维场景，不加入运行中的多租户发布或绕过素材权限，不把本轮原创样片作为内容检索验收证据。

不要将“50 项原型检查通过”写成“Hypit / OpenMontage 联调通过”。
